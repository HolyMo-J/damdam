# 트러블슈팅과 설계 하이라이트

겪은 문제와 해결 과정, 코드에서 의도적으로 설계한 부분을 기록한다. 포트폴리오로 쓸 수 있게 "증상, 원인, 해결, 배운 점" 순서로 쓴다. 해결한 문제와 의미 있는 구현이 생길 때마다 추가한다. 실제 종목 코드, 계좌, 키, 토큰은 쓰지 않는다.

## 트러블슈팅

### 1. 모의 실행 결과가 실전용 안전장치 상태를 오염시킴
- 증상: 실제 주문을 한 번도 안 냈는데 `auto_sell_guard.json`이 이미 만들어져 있었다. 실전으로 전환하면 처음부터 정지 상태일 수 있는 상황
- 원인: 시간 청산의 `attemptAutoSell`이 결과가 `FAILED`가 아니면 무조건 `recordAttempt`를 호출했다. 모의 실행(`SIMULATED`)도 통과해서 손실 횟수가 쌓였다. 모의 실행에서는 포지션이 팔리지 않아 같은 종목이 매 평일 다시 판정되므로, 손실 종목 하나만으로 3일 뒤 "연속 손실 3회 정지"에 도달할 수 있었다
- 해결: 주문 결과가 실제로 접수된 경우(`PLACED`)에만 안전장치에 기록한다. 모의 실행은 로그만 남기고 끝낸다
- 배운 점: 모의 모드는 "주문만 안 보내는 것"이 아니라 "부작용이 전혀 없는 것"이어야 한다. 상태를 쓰는 코드는 모의 모드에서도 실행되는지 따져봐야 한다

### 2. 안전장치가 실패하면 열려 있었음 (fail-open)
- 증상: 안전장치 상태 파일이 깨지거나 읽히지 않으면 초기 상태로 되돌아가 정지 상태가 풀렸다. 하루 자동 매도 횟수는 메모리에만 있어서 재시작하면 0이 됐다
- 원인: "읽기 실패 시 초기값" 패턴은 편해 보이지만, 안전장치에서는 오류가 곧 제한 해제를 뜻한다
- 해결
  - 파일이 있는데 못 읽으면 정지 상태로 취급한다. 파일이 없으면 처음 실행이거나 사용자가 정지를 풀려고 지운 것이므로 초기 상태로 본다 (정지 해제 수단으로 남긴 것)
  - 하루 횟수도 파일에 저장해서 재시작해도 유지한다
  - 저장에 실패하면 파일이 최신이 아니므로 저장에 성공할 때까지 주문을 막는다
  - 임시 파일에 쓴 뒤 원자적으로 교체해서, 쓰는 도중 종료돼도 깨진 파일이 남지 않게 한다
  - 단위 테스트 11개: 재시작 유지, 날짜 변경 시 초기화, 깨진 파일, 저장 실패, 정지 해제, 예전 형식 호환
- 배운 점: 안전 장치는 "오류가 났을 때 어느 쪽으로 넘어지는가"를 먼저 정해야 한다. 정상 경로가 아니라 실패 경로에 테스트를 더 쏟는다

### 3. Jackson 3에서 새 필드를 추가하자 예전 파일이 읽히지 않음
- 증상: 새 필드를 넣은 뒤 예전 형식 상태 파일을 읽는 테스트가 실패했다. fail-closed로 바꿨기 때문에 이 실패는 "실제 파일이 지금 정지로 취급되는 사고"로 이어질 뻔했다
- 원인: Jackson 3는 없는 값을 `int` 같은 기본형에 넣으면 실패한다(`FAIL_ON_NULL_FOR_PRIMITIVES` 기본 켜짐)
- 해결: 새 필드만 `Integer`로 두었다. 전역 설정을 끄는 방법도 있었지만, 그러면 손상된 `consecutiveLosses` 같은 핵심 필드도 조용히 0으로 읽혀 다시 fail-open이 된다. 핵심 필드는 엄격하게 두고 새 필드만 관대하게 했다
- 배운 점: 실제 운영 파일 형식과의 하위 호환은 테스트로 고정해야 한다. 라이브러리 메이저 버전의 기본값 변화도 실제로 부딪혀 봐야 알 수 있다

### 4. Windows에서 토큰 파일 권한 설정이 동작하지 않음
- 증상: 토큰 저장 시 `setReadable(false, false)`로 "소유자만 읽기"를 걸었다고 믿었으나, 실제 ACL에 `BUILTIN\Users:(M)`이 남아 있었다
- 원인: `java.io.File`의 권한 메서드는 POSIX 권한 모델을 전제로 한다. Windows에서는 `setReadable(false)`가 `false`를 반환하고 아무 효과가 없다. 반환값을 확인하지 않아 실패가 조용히 묻혔다
- 확인 방법: 더미 파일로 반환값과 `icacls` 결과를 직접 확인했다 (실제 토큰 파일은 열지 않고 권한 정보만 조회)
- 해결: 파일 시스템에 맞는 표준 API를 쓴다. POSIX는 `rw-------`, Windows(NTFS)는 `AclFileAttributeView`로 소유자만 허용하는 ACL을 설정한다 (상속 항목이 통째로 제거됨). 외부 프로세스(`icacls`) 호출 없이 순수 Java로 처리했다
- 같이 고친 점: 기존에는 토큰을 쓴 다음에 권한을 제한해서 그 사이 잠깐 기본 권한으로 존재했다. 이제는 빈 파일을 먼저 만들어 권한을 제한한 뒤 내용을 쓴다. 제한에 실패하면 조용히 넘기지 않고 경고를 남긴다
- 검증: 실제 파일의 ACL을 읽어 "항목이 소유자 하나뿐"인지 확인하는 테스트로 고정했다. 이미 느슨한 권한으로 있던 파일도 다음 저장 때 조여지는 것까지 확인한다
- 배운 점: "코드에 썼다"와 "동작한다"는 다르다. 보안 설정은 결과(실제 ACL)를 관찰해서 검증한다

### 5. 매도 접수 직후 OCO를 취소해 손절 보호가 사라질 수 있었음
- 증상: 시간 청산이 시장가 매도를 낸 직후, 체결 확인 전에 남은 OCO(익절/손절 조건주문)를 취소했다
- 원인: 주문 API 응답은 "접수"일 뿐 "체결"이 아니다. 접수 후 거부되거나(하한가, VI, 거래정지) 체결이 안 되면 포지션은 그대로인데 손절 보호만 사라진다
- 해결: 웹소켓의 SELL FILL(완전 체결) 이벤트를 받은 뒤에만 정리한다. 보유가 0이면 OCO 취소, 일부만 팔렸으면 기존 OCO 수량만 남은 보유량에 맞춘다. 남은 보유가 있는데 OCO가 없는 종목에는 새로 만들지 않는다 (관리 범위 밖일 수 있어서). PARTIAL_FILL에는 반응하지 않아 진행 중인 매도를 건드리지 않는다
- 이 덕분에 사용자가 직접 판 경우도 같은 경로로 정리된다. 시간 청산 주문에 묶는 방식보다 범위가 넓고 단순하다
- 테스트: Mockito로 협력 객체를 가짜로 바꿔 "보유 0이면 취소, 일부 남으면 취소 안 함, 오류가 나도 웹소켓 루프는 계속" 규칙을 6개 케이스로 고정
- 남은 한계: 체결 이벤트 직후 보유 조회가 잠시 이전 값을 줄 가능성이 있다. 그 경우 OCO가 남지만, 재동기화가 정리한다 (아래 10번)
- 배운 점: 비동기 주문에서는 "요청 성공"과 "상태 변경 완료"를 구분해서, 되돌리기 어려운 후속 조치(보호 장치 해제)는 확정 이벤트에 걸어야 한다

### 6. 외부 리뷰를 그대로 믿지 않고 공식 문서로 교차 검증
- 상황: 다른 AI 대화에서 나온 수정 목록에 추정이 섞여 있었다. 그대로 적용하지 않고 항목마다 코드와 공식 명세(OpenAPI JSON)로 확인했다
- 결과 예시
  - OCO 손절을 시장가로 걸 수 있는가: 명세에 "OCO/OTO는 지정가(LIMIT)만 지원"이 있어 불가. 지금 구조가 유일한 선택지임을 확인
  - 국내 OCO 가격이 호가 단위와 안 맞을 가능성: 문서에 "호가 단위에 맞아야 함, 어긋나면 400과 `nearestPrices`"가 명시돼 있고 코드는 정수 반올림만 해서 사실상 확실히 어긋난다는 것을 확인 (리뷰의 "가능성"보다 심각했다)
  - "보유 종목 중 OCO 없는 종목을 등록"이라는 지시는 그대로 하면 관리 범위 밖의 기존 보유 종목까지 매도 주문을 걸게 돼서 기존 결정과 충돌한다고 판단해 범위를 제한
- 배운 점: 돈이 움직이는 코드에서는 지시의 출처보다 근거를 본다. 확인하지 못한 것(실제 API 응답 등)은 "확인 못 함"으로 표시한다

### 7. "봇 종료" 알림이 실제로는 나가지 않는 구조였음
- 증상: 종료 알림을 JVM 종료 훅에 걸면 될 거라고 설계했지만, 봇을 끄는 `stop-listen.ps1`은 `Stop-Process`(프로세스 강제 종료)를 쓴다
- 원인: 강제 종료는 JVM 종료 훅을 실행하지 못한다. 즉 정상적으로 끌 때조차 종료 알림이 안 나가는 구조였다. 코드만 읽어서는 드러나지 않고, 스크립트와 코드를 함께 봐야 보이는 문제
- 해결: 종료 요청 파일(`bot/data/shutdown.request`)을 도입했다. 스크립트가 이 파일을 만들면 봇이 5초 안에 감지해 스스로 정상 종료(훅 실행, 알림 발송)하고, 15초 안에 안 끝나면 그때만 강제 종료한다. 스케줄러 스레드에서 `System.exit`를 직접 부르면 종료 훅과 스케줄러 정리가 서로 기다릴 수 있어 별도 스레드에서 호출한다
- 남은 한계: PC가 꺼지거나 프로세스가 크래시하는 경우에는 봇이 스스로 알릴 수 없다. 이건 외부 감시(하트비트)가 있어야 해결되므로 한계로 기록해 둔다
- 배운 점: 기능의 "성공 경로"를 끝까지 따라가서 실제로 그 코드가 실행되는지 확인해야 한다. 설계가 그럴듯해도 운영 스크립트가 그 경로를 우회할 수 있다

### 8. 알림 웹훅 주소가 로그로 새는 경로
- 위험: 디스코드 웹훅 주소에는 토큰이 들어 있다. Spring `RestClient`의 I/O 예외 메시지에는 요청 URL이 그대로 들어가므로, 평소처럼 `e.getMessage()`를 로그에 남기면 비밀값이 로그 파일에 기록된다
- 해결: 알림 전송 실패 시 예외 메시지 대신 HTTP 상태 코드나 예외 종류만 남긴다. 주소가 `https://discord.com/api/webhooks/`로 시작하지 않으면 값을 출력하지 않고 알림을 비활성화한다 (설정 실수로 다른 곳에 알림이 새는 것도 방지). `@everyone` 같은 멘션이 동작하지 않도록 `allowed_mentions`를 비운다
- 검증: 로그 캡처 어펜더로 "실패해도 예외를 던지지 않고, 로그에 토큰과 도메인이 없다"를 테스트로 고정했다
- 배운 점: 비밀값은 저장 위치뿐 아니라 "라이브러리가 대신 만들어 주는 문자열(예외 메시지)"을 통해서도 샌다

### 9. 국내 OCO 가격이 호가 단위와 안 맞아 등록이 거의 확실히 거부되는 구조였음
- 증상: 코드는 국내 가격을 정수로만 반올림했다. 손절 지정가는 감시가에서 1원을 뺐다. 미국 종목(달러 소수점 규칙)으로만 실제 검증했고, 국내 OCO는 모의 실행이라 API에 나간 적이 없었다
- 원인: 공식 명세는 "국내 가격은 호가 단위에 맞아야 함 (50,000~200,000원은 100원 단위)"이고 어긋나면 400과 함께 `tickSize`, `nearestPrices`를 준다. 2,000원 이상 종목은 정수 반올림만으로 호가에 맞을 확률이 낮고, "1원 빼기"는 사실상 항상 어긋난다. 모의 실행이라 드러나지 않았다
- 선택지: 호가표를 코드에 하드코딩하는 방법도 있었지만 공식 문서에 전체 구간표가 없어 추측이 된다. 그래서 서버가 400 응답으로 알려주는 값만 근거로 삼았다
- 해결: 응답의 `data.field`로 어느 지정가인지 판별해 익절은 위쪽, 손절은 아래쪽 이웃 호가로 옮겨 다시 보낸다. 두 방향 모두 나에게 불리하지 않은 쪽이다(더 높은 가격에 팔림, 더 확실히 체결됨)
- 돈이 걸린 경로라서 보수적인 안전 제한을 뒀다
  - 이동은 한 호가 이내, 방향이 반대이거나 모르는 필드, 파싱할 수 없는 응답은 보정하지 않고 실패 처리 후 알림
  - 재시도는 최대 2회. 재시도마다 새 clientOrderId를 써서 서버의 멱등성 캐시와 충돌하지 않게 함 (거부된 요청은 주문이 생기지 않았으므로 중복 위험 없음)
  - 감시가는 건드리지 않는다. 감시가가 호가 단위 검증 대상인지는 문서에 없어서, 그 경우는 보정 없이 실패로 드러나게 했다
- 검증: `MockRestServiceServer`로 "익절 보정 후 손절 보정, 두 번째와 세 번째 요청의 본문과 clientOrderId, 재시도 상한, 403은 재시도 안 함, 수정 API에도 동일 적용"을 확인. 실제 국내 종목 응답으로는 아직 확인하지 못했다(한계)
- 배운 점: 모의 모드로만 검증한 경로는 검증한 것이 아니다. 그리고 규칙을 모를 때는 추측해서 채우기보다 서버가 알려주는 값을 근거로 삼는 편이 안전하다

### 10. 재동기화가 이름뿐이었음: 로그만 남기고, 시작 때는 안 돌고, 타이밍도 틀렸음
- 증상: 웹소켓이 끊겼다 붙어도 끊긴 사이의 체결이 CSV에 없고 OCO도 등록되지 않았다
- 원인은 하나가 아니라 셋이 겹쳐 있었다
  1. `resync()`가 진행중 주문 개수를 로그로 남길 뿐이었다
  2. 봇 시작 때는 아예 호출되지 않았고, 연결 실패 경로에서도 호출되지 않았다
  3. 재연결이 끝나기도 전에(끊긴 직후) 실행됐다. 그러면 REST 조회와 재구독 사이의 짧은 틈에 생긴 체결은 어느 쪽에서도 못 받는다
- 해결
  - 구독이 확정(ack)된 뒤에 재동기화를 실행한다. 이후의 체결은 이벤트로 받고, 그 이전은 REST가 채우므로 틈이 없다. 봇 시작과 모든 재연결이 같은 경로를 탄다
  - 놓친 체결을 CSV에 기록하고, 끊긴 사이 완전히 팔린 종목의 OCO를 정리하고, 관리 범위 안의 보유 종목 중 OCO가 없거나 수량이 어긋난 것을 등록/수정한다. 관리 범위 밖의 기존 보유 종목은 건드리지 않는다
  - 별도 스레드에서 실행해서 PING과 재연결 스케줄이 REST 호출에 막히지 않게 했다
- 중복 기록 방지: 웹소켓과 재동기화가 같은 체결을 각각 기록할 수 있어서 (주문ID, 누적 체결수량)을 멱등 키로 삼았다. 웹소켓은 "10", REST는 "10.000"처럼 표기가 다를 수 있어 숫자로 정규화해 비교하고, 재시작 뒤에도 파일에서 키를 복원한다
- 스키마 변경 대응: 늦게 기록된 행은 `timestamp`(기록 시각)가 실제 체결 시각과 달라서 `filled_at`, `source` 컬럼을 추가했다. 컬럼 수가 다른 행이 섞이면 pandas가 파일을 못 읽으므로, 옛 형식 파일은 처음 기록할 때 임시 파일을 거쳐 통째로 새 형식으로 옮긴다 (기존 행 유지, 테스트로 고정)
- 배운 점: "재동기화한다"는 문장이 코드에서 실제로 무엇을 하는지, 언제 실행되는지, 실행 시점이 맞는지를 각각 확인해야 한다. 그리고 두 경로가 같은 데이터를 쓰면 멱등 키부터 정해야 한다

### 11. 봇이 사용자가 앱에서 직접 건 조건주문을 덮어쓸 수 있었음
- 발견: 재동기화를 설계하며 조건주문 목록 API 명세를 읽다가, 이 API가 다른 채널(토스 앱)에서 만든 조건주문도 함께 돌려준다는 것을 확인했다
- 원인: 봇은 종목의 진행 중 조건주문을 조회해 "첫 번째 것"을 OCO로 보고 수정했다. 사용자가 앱에서 같은 종목에 단일(SINGLE) 조건주문을 걸어 두었다면, 봇이 그것을 OCO로 바꿔 덮어쓸 수 있었다 (수정 API는 타입 전환을 허용한다)
- 해결: 응답 중 타입이 OCO인 것만 봇의 관리 대상으로 본다. 단일 조건주문은 종목당 개수 제한이 없어 OCO와 공존하므로 건드릴 이유가 없다
- 남은 한계: 사용자가 앱에서 직접 만든 OCO는 봇이 만든 것과 구별할 수 없다 (응답에 clientOrderId가 없음). 종목당 OCO는 1개뿐이라 그 경우 봇이 수정하게 된다
- 배운 점: 외부 API가 "내 것만" 돌려줄 거라고 가정하지 말고, 목록 조회 명세의 범위 설명을 읽어야 한다

### 12. CI를 붙이기 전에 "깨끗한 환경에서 통과하는가"를 먼저 확인
- 상황: push마다 테스트를 돌리는 GitHub Actions를 붙이려는데, 내 PC에는 `.env`(키, 시크릿)가 있고 CI에는 없다. 이 차이 때문에 CI에서만 실패하는 일이 흔하다
- 확인: 저장소를 임시 폴더에 새로 복제해 `.env` 없이 `./gradlew test`를 돌렸다. 설정 파일이 `${TOSS_API_KEY}` 같은 환경변수를 참조하는데도 전체 통과했다. 기본 실행과 테스트는 실제 API를 호출하지 않도록 프로필로 분리해 두었기 때문이다. 기능을 더할 때마다 같은 방식으로 다시 확인한다
- CI에서만 드러날 뻔한 문제: `bot/gradlew`의 git 파일 모드가 `100644`(실행 권한 없음)였다. Windows에서는 문제없지만 Linux 러너에서는 `Permission denied`로 실패한다. `git update-index --chmod=+x`로 저장소에 실행 권한을 기록해 CI 단계를 단순하게 유지했다
- 액션 버전은 기억에 의존하지 않고 각 저장소의 최신 릴리스를 조회해서 정했다. 시크릿이 필요 없으므로 워크플로 권한은 `contents: read`만 준다
- 실주문 경로 테스트: `MockRestServiceServer`로 요청 주소, 헤더, 본문을 검증한다. "시장가 주문에는 price가 없어야 한다" 같은, 틀리면 돈 문제가 되는 계약을 테스트로 고정했다. 요청은 가짜 서버가 가로채서 실제 API로 나가지 않는다
- 배운 점: 테스트가 통과한다는 것과 "다른 환경에서도 통과한다"는 다르다. 환경 차이(시크릿, 파일 권한, 줄바꿈)를 의심하며 깨끗한 복제본에서 검증하는 습관이 필요하다

## 설계 하이라이트

### 실주문 다중 잠금
자동 매도는 한 겹이 아니라 여러 겹을 모두 통과해야 실제로 나간다.
- `damdam.orders.live-mode` 기본값 false (모의 실행). 켜려면 `.env`에 직접 추가해야 한다
- 관리 범위 게이트(`ManagedScopeGate`): 기능을 처음 켠 시각 이후에 산 종목만 대상. 그 전부터 갖고 있던 종목은 알림만
- 1회 주문 금액 한도(국내, 해외 각각), 하루 최대 횟수, 연속 손실 시 자동 정지 (`AutoSellGuard`)
- 개발 도구(Claude Code)는 주문 엔드포인트를 직접 호출하지 않는다는 규칙을 문서로 고정하고, 테스트는 실제 주소가 아닌 도달 불가능한 주소를 써서 호출되면 바로 드러나게 했다

### 포지션 시작 시점을 주문 이력에서 복원 (`PositionEntryResolver`)
- 보유 종목의 "보유 시작일"은 API가 직접 주지 않는다. 최근 30일 체결 주문을 FIFO로 리플레이해서 포지션이 0이었다가 다시 쌓인 시점의 첫 매수를 시작으로 판단한다. 같은 종목을 하루에 여러 번 사고파는 매매 스타일도 처리된다
- 조회 범위 안에서 매수 기록을 못 찾으면 "그보다 오래 보유 중"으로 해석하고 알림만 남긴다. 순수 계산 로직이라 가짜 데이터로 단위 테스트한다

### 웹소켓 연결 관리 (`OrderStreamClient`)
- 지수 백오프(최대 30초) + 지터로 재연결. 서버 부하와 동시 재접속 쏠림을 피한다
- 토큰은 클라이언트당 1개만 유효하므로, 재연결 전에 이전 연결을 먼저 닫아야 새 연결이 밀려나지 않는다
- 끊긴 구간의 이벤트는 재전송되지 않는다는 API 특성 때문에, 구독이 확정된 직후 REST로 재동기화해 놓친 체결 기록, 남은 OCO 정리, 누락된 OCO 등록을 한다 (아래 10번)

### 테스트 가능한 구조와 CI 전제
- 외부 API를 부르는 실행기(query, listen, export 계열)는 프로필로 분리해서, 기본 빌드와 테스트는 실제 API를 호출하지 않는다
- `.env`가 없는 깨끗한 복제본에서 `./gradlew test`가 전체 통과하는 것을 확인했다 (CI에서 시크릿 없이 돌리기 위한 전제)

### 백테스트 데이터 수집 (`backtest` 패키지)
- 일봉을 `before`/`nextBefore`로 과거까지 페이지네이션. 타임존 오프셋의 `+`가 쿼리스트링에서 공백으로 오인되므로 반드시 인코딩한다
- 429는 `Retry-After`만큼 대기 후 재시도. 종목군은 거래대금 상위에서 ETF/ETN을 걸러 일반 보통주만 남긴다 (안 거르면 대형주 취지와 안 맞는 상품이 섞임)
- 봇과 분석(Python + pandas)은 CSV로만 연결해서 서로의 코드에 의존하지 않는다

### 문서로 남긴 판단의 이유
- 전략 문서에 청산 규칙의 근거, 한계(생존 편향 포함), 실전 전환 기준을 백테스트 결과를 보기 전에 확정한다는 원칙을 적었다. 결과를 본 뒤 기준을 바꾸면 사후 합리화가 되기 때문이다

### 알림과 수동 정지 (`notification`, `control` 패키지)
- 알림 채널은 `Notifier` 인터페이스 뒤에 두고 디스코드 구현체를 꽂았다. 호출하는 쪽(안전장치, OCO 관리, 웹소켓)은 디스코드를 모르고, 테스트에서는 람다 한 줄로 가짜 알림기를 넣는다
- 같은 사건은 시간당 한 번만 나가게 스로틀하고(같은 장애가 반복돼도 알림이 폭주하지 않음), 전송은 별도 스레드로 해서 알림 지연이 매매 경로를 막지 않는다
- 403은 모든 토스 API 호출이 지나가는 공용 `RestClient`의 인터셉터 한 곳에서 감지한다. 호출 지점마다 예외 처리를 넣는 것보다 누락이 없다
- 정지 파일은 재시작 없이 파일 하나로 자동 매도와 OCO 등록을 멈추는 스위치다. 결정 시점마다 파일을 확인하고 상태가 바뀔 때만 알린다. 보호 장치를 걷어내는 OCO 취소는 막지 않고, 존재 여부를 판단할 수 없으면 멈추는 쪽으로 넘어지게 했다. 이미 서버에 등록된 OCO는 계속 동작한다는 한계를 운영 문서에 명시했다
