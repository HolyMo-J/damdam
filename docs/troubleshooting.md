# 트러블슈팅과 설계 하이라이트

겪은 문제와 해결 과정, 코드에서 의도적으로 설계한 부분을 기록한다. 포트폴리오로 쓸 수 있게 "증상, 원인, 해결, 배운 점" 순서로 쓴다. 해결한 문제와 의미 있는 구현이 생길 때마다 추가한다. 실제 종목 코드, 계좌, 키, 토큰은 쓰지 않는다.

## 트러블슈팅

### 1. 모의 실행 결과가 실전용 안전장치 상태를 오염시킴
- 증상: 실제 주문을 한 번도 안 냈는데 `auto_sell_guard.json`이 이미 만들어져 있었다. 실전으로 전환하면 처음부터 정지 상태일 수 있는 상황
- 원인: 시간 청산의 `attemptAutoSell`이 결과가 `FAILED`가 아니면 무조건 `recordAttempt`를 호출했다. 모의 실행(`SIMULATED`)도 통과해서 손실 횟수가 쌓였다. 모의 실행에서는 포지션이 팔리지 않아 같은 종목이 매 평일 다시 판정되므로, 손실 종목 하나만으로 3일 뒤 "연속 손실 3회 정지"에 도달할 수 있었다
- 해결: 주문 결과가 실제로 접수된 경우(`PLACED`)에만 안전장치에 기록한다. 모의 실행은 로그만 남기고 끝낸다
- 배운 점: 모의 모드는 "주문만 안 보내는 것"이 아니라 "부작용이 전혀 없는 것"이어야 한다. 상태를 쓰는 코드는 모의 모드에서도 실행되는지 따져봐야 한다

### 2. 안전장치가 실패하면 열려 있었음 (fail-open)
- 증상: 안전장치 상태 파일이 깨지거나 읽히지 않으면 초기 상태로 되돌아가 정지 상태가 풀렸다. 하루 자동 매도 횟수는 메모리에만 있어서 재시작하면 0이 됐다
- 원인: "읽기 실패 시 초기값" 패턴은 편해 보이지만, 안전장치에서는 오류가 곧 제한 해제를 뜻한다
- 해결
  - 파일이 있는데 못 읽으면 정지 상태로 취급한다. 파일이 없으면 처음 실행이거나 사용자가 정지를 풀려고 지운 것이므로 초기 상태로 본다 (정지 해제 수단으로 남긴 것)
  - 하루 횟수도 파일에 저장해서 재시작해도 유지한다
  - 저장에 실패하면 파일이 최신이 아니므로 저장에 성공할 때까지 주문을 막는다
  - 임시 파일에 쓴 뒤 원자적으로 교체해서, 쓰는 도중 종료돼도 깨진 파일이 남지 않게 한다
  - 단위 테스트 11개: 재시작 유지, 날짜 변경 시 초기화, 깨진 파일, 저장 실패, 정지 해제, 예전 형식 호환
- 배운 점: 안전 장치는 "오류가 났을 때 어느 쪽으로 넘어지는가"를 먼저 정해야 한다. 정상 경로가 아니라 실패 경로에 테스트를 더 쏟는다

### 3. Jackson 3에서 새 필드를 추가하자 예전 파일이 읽히지 않음
- 증상: 새 필드를 넣은 뒤 예전 형식 상태 파일을 읽는 테스트가 실패했다. fail-closed로 바꿨기 때문에 이 실패는 "실제 파일이 지금 정지로 취급되는 사고"로 이어질 뻔했다
- 원인: Jackson 3는 없는 값을 `int` 같은 기본형에 넣으면 실패한다(`FAIL_ON_NULL_FOR_PRIMITIVES` 기본 켜짐)
- 해결: 새 필드만 `Integer`로 두었다. 전역 설정을 끄는 방법도 있었지만, 그러면 손상된 `consecutiveLosses` 같은 핵심 필드도 조용히 0으로 읽혀 다시 fail-open이 된다. 핵심 필드는 엄격하게 두고 새 필드만 관대하게 했다
- 배운 점: 실제 운영 파일 형식과의 하위 호환은 테스트로 고정해야 한다. 라이브러리 메이저 버전의 기본값 변화도 실제로 부딪혀 봐야 알 수 있다

### 4. Windows에서 토큰 파일 권한 설정이 동작하지 않음
- 증상: 토큰 저장 시 `setReadable(false, false)`로 "소유자만 읽기"를 걸었다고 믿었으나, 실제 ACL에 `BUILTIN\Users:(M)`이 남아 있었다
- 원인: `java.io.File`의 권한 메서드는 POSIX 권한 모델을 전제로 한다. Windows에서는 `setReadable(false)`가 `false`를 반환하고 아무 효과가 없다. 반환값을 확인하지 않아 실패가 조용히 묻혔다
- 확인 방법: 더미 파일로 반환값과 `icacls` 결과를 직접 확인했다 (실제 토큰 파일은 열지 않고 권한 정보만 조회)
- 해결: 파일 시스템에 맞는 표준 API를 쓴다. POSIX는 `rw-------`, Windows(NTFS)는 `AclFileAttributeView`로 소유자만 허용하는 ACL을 설정한다 (상속 항목이 통째로 제거됨). 외부 프로세스(`icacls`) 호출 없이 순수 Java로 처리했다
- 같이 고친 점: 기존에는 토큰을 쓴 다음에 권한을 제한해서 그 사이 잠깐 기본 권한으로 존재했다. 이제는 빈 파일을 먼저 만들어 권한을 제한한 뒤 내용을 쓴다. 제한에 실패하면 조용히 넘기지 않고 경고를 남긴다
- 검증: 실제 파일의 ACL을 읽어 "항목이 소유자 하나뿐"인지 확인하는 테스트로 고정했다. 이미 느슨한 권한으로 있던 파일도 다음 저장 때 조여지는 것까지 확인한다
- 배운 점: "코드에 썼다"와 "동작한다"는 다르다. 보안 설정은 결과(실제 ACL)를 관찰해서 검증한다

### 5. 매도 접수 직후 OCO를 취소해 손절 보호가 사라질 수 있었음
- 증상: 시간 청산이 시장가 매도를 낸 직후, 체결 확인 전에 남은 OCO(익절/손절 조건주문)를 취소했다
- 원인: 주문 API 응답은 "접수"일 뿐 "체결"이 아니다. 접수 후 거부되거나(하한가, VI, 거래정지) 체결이 안 되면 포지션은 그대로인데 손절 보호만 사라진다
- 해결: 웹소켓의 SELL FILL(완전 체결) 이벤트를 받은 뒤에만 정리한다. 보유가 0이면 OCO 취소, 일부만 팔렸으면 기존 OCO 수량만 남은 보유량에 맞춘다. 남은 보유가 있는데 OCO가 없는 종목에는 새로 만들지 않는다 (관리 범위 밖일 수 있어서). PARTIAL_FILL에는 반응하지 않아 진행 중인 매도를 건드리지 않는다
- 이 덕분에 사용자가 직접 판 경우도 같은 경로로 정리된다. 시간 청산 주문에 묶는 방식보다 범위가 넓고 단순하다
- 테스트: Mockito로 협력 객체를 가짜로 바꿔 "보유 0이면 취소, 일부 남으면 취소 안 함, 오류가 나도 웹소켓 루프는 계속" 규칙을 6개 케이스로 고정
- 남은 한계: 체결 이벤트 직후 보유 조회가 잠시 이전 값을 줄 가능성이 있다. 그 경우 OCO가 남지만, 재동기화가 정리한다 (아래 10번)
- 배운 점: 비동기 주문에서는 "요청 성공"과 "상태 변경 완료"를 구분해서, 되돌리기 어려운 후속 조치(보호 장치 해제)는 확정 이벤트에 걸어야 한다

### 6. 외부 리뷰를 그대로 믿지 않고 공식 문서로 교차 검증
- 상황: 다른 AI 대화에서 나온 수정 목록에 추정이 섞여 있었다. 그대로 적용하지 않고 항목마다 코드와 공식 명세(OpenAPI JSON)로 확인했다
- 결과 예시
  - OCO 손절을 시장가로 걸 수 있는가: 명세에 "OCO/OTO는 지정가(LIMIT)만 지원"이 있어 불가. 지금 구조가 유일한 선택지임을 확인
  - 국내 OCO 가격이 호가 단위와 안 맞을 가능성: 문서에 "호가 단위에 맞아야 함, 어긋나면 400과 `nearestPrices`"가 명시돼 있고 코드는 정수 반올림만 해서 사실상 확실히 어긋난다는 것을 확인 (리뷰의 "가능성"보다 심각했다)
  - "보유 종목 중 OCO 없는 종목을 등록"이라는 지시는 그대로 하면 관리 범위 밖의 기존 보유 종목까지 매도 주문을 걸게 돼서 기존 결정과 충돌한다고 판단해 범위를 제한
- 배운 점: 돈이 움직이는 코드에서는 지시의 출처보다 근거를 본다. 확인하지 못한 것(실제 API 응답 등)은 "확인 못 함"으로 표시한다

### 7. "봇 종료" 알림이 실제로는 나가지 않는 구조였음
- 증상: 종료 알림을 JVM 종료 훅에 걸면 될 거라고 설계했지만, 봇을 끄는 `stop-listen.ps1`은 `Stop-Process`(프로세스 강제 종료)를 쓴다
- 원인: 강제 종료는 JVM 종료 훅을 실행하지 못한다. 즉 정상적으로 끌 때조차 종료 알림이 안 나가는 구조였다. 코드만 읽어서는 드러나지 않고, 스크립트와 코드를 함께 봐야 보이는 문제
- 해결: 종료 요청 파일(`bot/data/shutdown.request`)을 도입했다. 스크립트가 이 파일을 만들면 봇이 5초 안에 감지해 스스로 정상 종료(훅 실행, 알림 발송)하고, 15초 안에 안 끝나면 그때만 강제 종료한다. 스케줄러 스레드에서 `System.exit`를 직접 부르면 종료 훅과 스케줄러 정리가 서로 기다릴 수 있어 별도 스레드에서 호출한다
- 남은 한계: PC가 꺼지거나 프로세스가 크래시하는 경우에는 봇이 스스로 알릴 수 없다. 이건 외부 감시(하트비트)가 있어야 해결되므로 한계로 기록해 둔다
- 배운 점: 기능의 "성공 경로"를 끝까지 따라가서 실제로 그 코드가 실행되는지 확인해야 한다. 설계가 그럴듯해도 운영 스크립트가 그 경로를 우회할 수 있다

### 8. 알림 웹훅 주소가 로그로 새는 경로
- 위험: 디스코드 웹훅 주소에는 토큰이 들어 있다. Spring `RestClient`의 I/O 예외 메시지에는 요청 URL이 그대로 들어가므로, 평소처럼 `e.getMessage()`를 로그에 남기면 비밀값이 로그 파일에 기록된다
- 해결: 알림 전송 실패 시 예외 메시지 대신 HTTP 상태 코드나 예외 종류만 남긴다. 주소가 `https://discord.com/api/webhooks/`로 시작하지 않으면 값을 출력하지 않고 알림을 비활성화한다 (설정 실수로 다른 곳에 알림이 새는 것도 방지). `@everyone` 같은 멘션이 동작하지 않도록 `allowed_mentions`를 비운다
- 검증: 로그 캡처 어펜더로 "실패해도 예외를 던지지 않고, 로그에 토큰과 도메인이 없다"를 테스트로 고정했다
- 배운 점: 비밀값은 저장 위치뿐 아니라 "라이브러리가 대신 만들어 주는 문자열(예외 메시지)"을 통해서도 샌다

### 9. 국내 OCO 가격이 호가 단위와 안 맞아 등록이 거의 확실히 거부되는 구조였음
- 증상: 코드는 국내 가격을 정수로만 반올림했다. 손절 지정가는 감시가에서 1원을 뺐다. 미국 종목(달러 소수점 규칙)으로만 실제 검증했고, 국내 OCO는 모의 실행이라 API에 나간 적이 없었다
- 원인: 공식 명세는 "국내 가격은 호가 단위에 맞아야 함 (50,000~200,000원은 100원 단위)"이고 어긋나면 400과 함께 `tickSize`, `nearestPrices`를 준다. 2,000원 이상 종목은 정수 반올림만으로 호가에 맞을 확률이 낮고, "1원 빼기"는 사실상 항상 어긋난다. 모의 실행이라 드러나지 않았다
- 선택지: 호가표를 코드에 하드코딩하는 방법도 있었지만 공식 문서에 전체 구간표가 없어 추측이 된다. 그래서 서버가 400 응답으로 알려주는 값만 근거로 삼았다
- 해결: 응답의 `data.field`로 어느 지정가인지 판별해 익절과 손절 모두 아래쪽 이웃 호가로 옮겨 다시 보낸다. 두 방향 모두 확실한 체결 쪽이다 (처음엔 익절을 위쪽으로 옮겼으나, 이후 review-task 10번에서 공식 명세를 다시 읽고 방향을 바꿨다. 아래 14번 참고)
- 돈이 걸린 경로라서 보수적인 안전 제한을 뒀다
  - 이동은 한 호가 이내, 방향이 반대이거나 모르는 필드, 파싱할 수 없는 응답은 보정하지 않고 실패 처리 후 알림
  - 재시도는 최대 2회. 재시도마다 새 clientOrderId를 써서 서버의 멱등성 캐시와 충돌하지 않게 함 (거부된 요청은 주문이 생기지 않았으므로 중복 위험 없음)
  - 감시가는 건드리지 않는다. 감시가가 호가 단위 검증 대상인지는 문서에 없어서, 그 경우는 보정 없이 실패로 드러나게 했다
- 검증: `MockRestServiceServer`로 "익절 보정 후 손절 보정, 두 번째와 세 번째 요청의 본문과 clientOrderId, 재시도 상한, 403은 재시도 안 함, 수정 API에도 동일 적용"을 확인. 실제 국내 종목 응답으로는 아직 확인하지 못했다(한계)
- 배운 점: 모의 모드로만 검증한 경로는 검증한 것이 아니다. 그리고 규칙을 모를 때는 추측해서 채우기보다 서버가 알려주는 값을 근거로 삼는 편이 안전하다

### 10. 재동기화가 이름뿐이었음: 로그만 남기고, 시작 때는 안 돌고, 타이밍도 틀렸음
- 증상: 웹소켓이 끊겼다 붙어도 끊긴 사이의 체결이 CSV에 없고 OCO도 등록되지 않았다
- 원인은 하나가 아니라 셋이 겹쳐 있었다
  1. `resync()`가 진행중 주문 개수를 로그로 남길 뿐이었다
  2. 봇 시작 때는 아예 호출되지 않았고, 연결 실패 경로에서도 호출되지 않았다
  3. 재연결이 끝나기도 전에(끊긴 직후) 실행됐다. 그러면 REST 조회와 재구독 사이의 짧은 틈에 생긴 체결은 어느 쪽에서도 못 받는다
- 해결
  - 구독이 확정(ack)된 뒤에 재동기화를 실행한다. 이후의 체결은 이벤트로 받고, 그 이전은 REST가 채우므로 틈이 없다. 봇 시작과 모든 재연결이 같은 경로를 탄다
  - 놓친 체결을 CSV에 기록하고, 끊긴 사이 완전히 팔린 종목의 OCO를 정리하고, 관리 범위 안의 보유 종목 중 OCO가 없거나 수량이 어긋난 것을 등록/수정한다. 관리 범위 밖의 기존 보유 종목은 건드리지 않는다
  - 별도 스레드에서 실행해서 PING과 재연결 스케줄이 REST 호출에 막히지 않게 했다
- 중복 기록 방지: 웹소켓과 재동기화가 같은 체결을 각각 기록할 수 있어서 (주문ID, 누적 체결수량)을 멱등 키로 삼았다. 웹소켓은 "10", REST는 "10.000"처럼 표기가 다를 수 있어 숫자로 정규화해 비교하고, 재시작 뒤에도 파일에서 키를 복원한다
- 스키마 변경 대응: 늦게 기록된 행은 `timestamp`(기록 시각)가 실제 체결 시각과 달라서 `filled_at`, `source` 컬럼을 추가했다. 컬럼 수가 다른 행이 섞이면 pandas가 파일을 못 읽으므로, 옛 형식 파일은 처음 기록할 때 임시 파일을 거쳐 통째로 새 형식으로 옮긴다 (기존 행 유지, 테스트로 고정)
- 배운 점: "재동기화한다"는 문장이 코드에서 실제로 무엇을 하는지, 언제 실행되는지, 실행 시점이 맞는지를 각각 확인해야 한다. 그리고 두 경로가 같은 데이터를 쓰면 멱등 키부터 정해야 한다

### 11. 봇이 사용자가 앱에서 직접 건 조건주문을 덮어쓸 수 있었음
- 발견: 재동기화를 설계하며 조건주문 목록 API 명세를 읽다가, 이 API가 다른 채널(토스 앱)에서 만든 조건주문도 함께 돌려준다는 것을 확인했다
- 원인: 봇은 종목의 진행 중 조건주문을 조회해 "첫 번째 것"을 OCO로 보고 수정했다. 사용자가 앱에서 같은 종목에 단일(SINGLE) 조건주문을 걸어 두었다면, 봇이 그것을 OCO로 바꿔 덮어쓸 수 있었다 (수정 API는 타입 전환을 허용한다)
- 해결: 응답 중 타입이 OCO인 것만 봇의 관리 대상으로 본다. 단일 조건주문은 종목당 개수 제한이 없어 OCO와 공존하므로 건드릴 이유가 없다
- 남은 한계: 사용자가 앱에서 직접 만든 OCO는 봇이 만든 것과 구별할 수 없다 (응답에 clientOrderId가 없음). 종목당 OCO는 1개뿐이라 그 경우 봇이 수정하게 된다
- 배운 점: 외부 API가 "내 것만" 돌려줄 거라고 가정하지 말고, 목록 조회 명세의 범위 설명을 읽어야 한다

### 12. CI를 붙이기 전에 "깨끗한 환경에서 통과하는가"를 먼저 확인
- 상황: push마다 테스트를 돌리는 GitHub Actions를 붙이려는데, 내 PC에는 `.env`(키, 시크릿)가 있고 CI에는 없다. 이 차이 때문에 CI에서만 실패하는 일이 흔하다
- 확인: 저장소를 임시 폴더에 새로 복제해 `.env` 없이 `./gradlew test`를 돌렸다. 설정 파일이 `${TOSS_API_KEY}` 같은 환경변수를 참조하는데도 전체 통과했다. 기본 실행과 테스트는 실제 API를 호출하지 않도록 프로필로 분리해 두었기 때문이다. 기능을 더할 때마다 같은 방식으로 다시 확인한다
- CI에서만 드러날 뻔한 문제: `bot/gradlew`의 git 파일 모드가 `100644`(실행 권한 없음)였다. Windows에서는 문제없지만 Linux 러너에서는 `Permission denied`로 실패한다. `git update-index --chmod=+x`로 저장소에 실행 권한을 기록해 CI 단계를 단순하게 유지했다
- 액션 버전은 기억에 의존하지 않고 각 저장소의 최신 릴리스를 조회해서 정했다. 시크릿이 필요 없으므로 워크플로 권한은 `contents: read`만 준다
- 실주문 경로 테스트: `MockRestServiceServer`로 요청 주소, 헤더, 본문을 검증한다. "시장가 주문에는 price가 없어야 한다" 같은, 틀리면 돈 문제가 되는 계약을 테스트로 고정했다. 요청은 가짜 서버가 가로채서 실제 API로 나가지 않는다
- 배운 점: 테스트가 통과한다는 것과 "다른 환경에서도 통과한다"는 다르다. 환경 차이(시크릿, 파일 권한, 줄바꿈)를 의심하며 깨끗한 복제본에서 검증하는 습관이 필요하다

### 13. 휴장일을 반영하려다 "목록 방식"이 아니라 라이브 조회를 쓰게 된 경우 (2026-09-23)
- 상황: `TradingDayCalculator`가 평일만 세서 국내 공휴일이 낀 주에는 시간 청산이 실제보다 하루 일찍 왔다. 처음 계획은 "휴장일 목록을 연 1회 수동 갱신"이었다 (토스 API에 캘린더 조회가 없을 거라고 예상했기 때문)
- 확인: 공식 명세(`openapi.json`)를 먼저 읽어보니 `GET /api/v1/market-calendar/KR`이 실제로 있었다. 날짜 하나를 넘기면 그날의 개장 여부와 전/후 영업일을 알려준다. 기간을 한 번에 조회하는 기능은 없다
- 방향 전환: 수동 목록 대신 이 API를 그때그때 호출하고 결과를 캐시하는 방식으로 설계를 바꿨다. 과거/오늘 날짜의 개장 여부는 나중에 바뀔 일이 없어서 캐시는 영구적이어도 안전하고, 매년 사람이 목록을 갱신할 필요도 없다. 시간 청산이 하루 한 번(평일 09:05)만 돌고 보유 종목도 적어 호출량 걱정도 없다
- 안전장치: 국내만 실제 캘린더를 쓰고 해외는 그대로 요일만 보는 근사치를 유지한다(해외는 자동 매도 없이 알림만 하므로). 캘린더 조회가 실패해도 예외를 던져 시간 청산 전체를 막지 않고, 요일만 보는 기존 방식으로 조용히 폴백한다(대신 로그를 남긴다)
- 배운 점: "이 기능은 API에 없을 것"이라는 가정도 실제로 명세를 열어 확인하기 전까지는 가정일 뿐이다. 대안(목록 방식)을 먼저 제안해두었더라도, 문서를 확인해서 더 나은 방법이 나오면 그쪽으로 바꾸는 게 맞다

### 14. 익절 지정가를 "유리한 가격"으로 옮기는 게 오히려 미체결 위험이었음 (2026-09-23)
- 상황: 9번에서 호가 단위 보정 방향을 익절은 위쪽(더 높은 가격), 손절은 아래쪽(더 확실한 체결)으로 정했다. 리뷰 항목(docs/review-tasks.md 10번)에서 "감시가에 닿아도 가격이 그 근처에 머물면 위쪽으로 옮긴 익절 지정가가 체결 안 될 수 있다"는 의견이 나왔다
- 확인: WebFetch로 명세를 조회하면 대용량 문서가 중간에 잘려서 관련 스키마가 안 보였다. `curl`로 `openapi.json` 전체를 받아 파이썬으로 직접 읽으니, `ConditionRequest.orderPrice` 설명에 "트리거 시 이 가격의 지정가 주문을 **생성**합니다"라고 적혀 있었다. 조건(leg) 상태값에도 `ORDERING`(생성 중), `ORDERED`(생성됨)가 `COMPLETED`(체결)와 별도로 있다. 이 두 정황으로 미루어 보면 감시가 도달이 곧바로 체결을 뜻하지는 않는 것으로 보이지만, 명세가 실행 엔진 동작을 문장으로 확정해 주지는 않는다(damdam-reviewer 검토에서 지적, 트리거 판정 기준이 체결가인지 호가인지도 인용문에 없음). 다만 이 방향성 결론(아래쪽이 더 안전)은 "감시가 도달=즉시 체결이 아니다"라는 해석의 확실성과 무관하게 표준적인 지정가 주문 의미론만으로도 성립한다
- 원인: 익절 지정가를 감시가보다 높게 옮기면, 감시가에 닿은 시점의 가격이 그 지정가까지 더 올라가지 못하고 반락할 경우 주문이 미체결로 남을 위험이 있다. "더 높은 가격에 팔린다"는 이득은 체결이 됐을 때 이야기이고, 체결 자체가 안 되는 위험을 과소평가했다
- 해결: 익절도 손절과 같은 방향(아래쪽 이웃 호가)으로 바꿨다. 감시가에 이미 도달한 시점이므로 그보다 낮은 지정가는 즉시 체결될 가능성이 높다. 가격이 한 호가만큼 살짝 불리해질 수 있지만, 이 봇의 1차 목적(감정 없이 규칙대로 청산하는 것)에는 미체결보다 확실한 체결이 낫다
- 검증: `TickSizeCorrectionTest`와 `ConditionalOrderServiceLiveTest`의 방향 관련 테스트를 새 방향에 맞게 갱신. `damdam-reviewer` 독립 검토에서 코드(대칭적으로 아래쪽만 허용, `AtrOcoPricing` 초기값 불변)는 확인했으나, 인용한 공식 문서 문구 자체는 도구 제약으로 재확인하지 못했음(caller가 직접 확인한 것으로 남김)
- 배운 점: 조사 도구(WebFetch 같은 요약형 도구)가 "문서에 없다"고 답해도, 그게 실제로 없는 것인지 도구가 잘라낸 것인지는 원본을 직접 받아봐야 안다. "가격이 유리하다"와 "주문이 체결된다"는 다른 문제이고, 지정가 주문에서는 체결 여부가 가격보다 우선이다. 그리고 정황 증거로부터의 추론은 "명세가 보여준다"처럼 확정형으로 쓰지 않는다

### 15. 해외 종목은 "알림만"이라고 해놓고 OCO는 실제로 자동 등록되고 있었음 (2026-09-23)
- 상황: 실전 전환 체크리스트를 만들며 사용자가 "미장도 지켜봐야 하나"라고 물어서 답하려고 코드를 다시 보니, 2026-09-19에 정한 "해외 종목 시간 청산은 알림만"이라는 규칙이 시간 청산에만 적용되고 ATR OCO(`AtrOcoManagementService`)에는 안 걸려 있었다
- 원인: `doSync()`가 통화(`isKrw`)를 가격 반올림 방식(정수 대 소수)을 고르는 데만 썼지, OCO를 걸지 말지 판단에는 안 썼다. 공식 명세에는 "해외 주식은 장 구분과 상관없이 거래 가능한 모든 시간대에 조건이 발동된다"고 돼 있어서, 실전 전환 후에는 해외 종목의 OCO가 미장 시간에도 실제로 걸리고 트리거될 수 있는 상태였다. 시간 청산과 OCO를 별도로 만들면서 정책을 한쪽에만 반영한 게 원인
- 해결: 시간 청산과 같은 원칙으로 맞췄다. `doSync()`에서 통화가 KRW가 아니면 OCO를 등록/수정하지 않고 알림만 보낸다. `ensureOco()`도 해외는 아무것도 안 하고 `false`(안 고침)를 돌려준다. `cancelIfOpen()`은 기존에 걸려 있던 해외 OCO를 취소하지 않고 그대로 둔다(사용자 선택, 필요하면 앱에서 직접 정리). 이번에 첫 실전은 국내 종목만으로 시작하기로 하면서 발견됐고, docs/strategy.md에 "해외는 시간 청산과 OCO 모두 알림만"으로 정책을 한 곳에 정리했다
- 검증: `AtrOcoManagementServiceTest`의 해외 관련 테스트를 새로 추가하고, 기존 테스트의 기본 보유 종목을 국내(KRW)로 바꿨다(원래 US/USD를 아무 의미 없이 기본값으로 썼던 것이라, 실제로는 관리 대상 국내 종목의 동작을 검증하고 있었을 뿐 해외를 의도적으로 테스트한 게 아니었다)
- damdam-reviewer 지적과 재확인: `cancelIfOpen()`이 국내/해외를 가르는 데 쓴 `ConditionalOrderDetail.market()` 필드는 예전 세션에서 이미 추가해둔 필드인데 실제 분기 로직에 처음 쓰인 것이 이번이었고, 이 필드가 실제 API 응답과 맞는 이름/값인지 이 저장소 안에서 한 번도 검증된 적이 없었다. 틀렸다면 Jackson이 조용히 `null`을 넣어 `!"KR".equals(null)`이 항상 참이 되고, 해외뿐 아니라 **국내 종목의 OCO 정리(5번 항목)까지 조용히 멈추는** 회귀가 될 뻔했다. `curl`로 `openapi.json` 원본을 다시 받아 `ConditionalOrderDetailResponse` 스키마를 확인한 결과 `market`이 필수 필드이고 enum이 정확히 `["KR","US"]`임을 재확인했다(오늘 9번 항목에서 쓴 것과 같은 방법). 다만 기존 테스트(`ConditionalOrderServiceLiveTest`)의 목 JSON에는 `market` 필드가 아예 없어서 실제 역직렬화 경로를 검증하지 못하고 있었기에, 목 응답에 `market`을 추가하고 이 필드가 실제로 역직렬화되는지 확인하는 테스트(`deserializesTheMarketFieldFromTheRealResponseShape`)를 새로 추가했다. `cancelIfOpen()`이 해외 OCO를 그대로 둘 때 로그만 남기던 것도 지적을 받아, 나중에 재매수 시 낡은 OCO가 새 수량/평단가와 안 맞을 수 있다는 알림을 추가했다
- 배운 점: 같은 정책("해외는 알림만")이 두 군데(시간 청산, OCO)에 따로 구현돼 있으면 한쪽만 고치고 잊기 쉽다. 그리고 테스트 픽스처에 아무 의미 없이 고른 값(여기서는 US/USD)이 나중에 그 값 자체가 의미를 갖게 되면(통화별로 동작이 갈리게 되면) 테스트가 의도와 다른 걸 검증하고 있었다는 게 드러난다. 또한 예전에 "이럴 것이다"로 추가해둔 필드가 실제 분기 로직에 처음 쓰이는 순간이야말로, 그 필드가 진짜 맞는지 다시 확인해야 할 때다

### 16. 문서에 "확인함"이라고 적은 일목 표시 이동이 근거 없는 값이었음 (2026-09-29)
- 상황: 3단계 전략 B(일목 구름 돌파) 신호를 구현하고 독립 검토(`damdam-reviewer`)를 맡겼더니, 표시 이동을 26칸으로 구현했는데 TradingView 계열은 25칸으로 그린다는 지적이 나왔다. docs/strategy.md에는 "표준 정의와 일치함을 확인함"이라고 적혀 있었지만 출처가 없었다
- 원인: 일목 설정값 26을 "26일 앞에 그린다"로 그대로 읽어 26칸으로 구현했고, 확인한 적 없는 것을 "확인함"으로 적었다. 25칸과 26칸은 구름 상단이 하루 어긋나 돌파일과 신호가 달라지는데, 기준은 사용자가 실제로 보는 토스 차트인데도 그 화면과 맞춰본 적이 없었다
- 해결: 검색과 증권사 도움말로는 결론이 나지 않아서(정의가 모호하고 토스 페이지는 로딩 실패) 사용자의 차트 스크린샷을 직접 측정했다. 볼륨 막대(봉마다 하나씩 규칙적인 간격)로 봉 간격과 봉 위치를 재고, 일봉 CSV에서 계산한 선행스팬2 곡선을 25칸과 26칸 각각으로 그렸을 때의 위치를 실제 경계선과 비교했다. POSCO홀딩스는 곡선 전체 244열을 비교했고 표시 이동마다 세로축 보정을 따로 최적화해 공정하게 견줬다 (오차 RMS 24칸 1.84px, 25칸 0.47px, 26칸 2.32px, 27칸 3.72px). 삼성전자는 계단 5곳이 25칸 예측과 1px 안팎으로 맞았고, NH투자증권은 CSV가 없어 급등 봉 하나의 두 흔적만 대조했다. 코드는 `DISPLACEMENT = 25`, 필요한 최소 봉 수 78로 확정했다
- 검증: 손계산 테스트가 처음에는 기준선 기간을 26에서 25로 바꾼 변형을 잡지 못했다. 봉마다 값이 다른 시리즈를 추가하고 코드를 일부러 14가지로 망가뜨려서 테스트가 실제로 실패하는지 확인했다
- 실수와 정정: 처음 받은 캡처가 CSV 없는 종목(005940, 의도한 005490과 달랐음)이었는데 알고도 그대로 진행했다. 측정 자체는 유효해서 NH 검증으로 남기고 올바른 종목을 추가로 검증했다
- 배운 점: 문서에 "확인함"이라고 쓰려면 무엇을 어떻게 확인했는지가 함께 있어야 한다. 정의가 여러 갈래인 지표는 "표준"이 아니라 사용자가 실제로 보는 화면을 기준으로 삼고, 화면 픽셀처럼 독립적인 관측을 한 번은 붙여봐야 한다. 테스트도 일부러 망가뜨린 코드에 실제로 실패하는지 봐야 믿을 수 있다

### 17. 조회용으로 넣으려던 타임아웃이 주문 경로에 "접수 여부 불명" 상태를 만들 뻔했음 (2026-09-30)
- 상황: 독립 검토가 "`tossRestClient`에 타임아웃이 없어 응답이 멈추면 호출 하나가 무한정 기다린다"고 지적했다(2026-09-29). 종목별 조회가 이어지는 가상매매 스캔을 붙이기 전에 막으려고 시작했는데, 값을 넣기 전에 이 클라이언트를 쓰는 곳을 확인하니 조회 서비스 9개뿐 아니라 시장가 매도(`OrderPlacementService`)와 조건주문도 같은 빈을 쓰고 있었다
- 원인: 지금은 무한 대기라서 타임아웃 예외가 난 적이 없었다. `OrderPlacementService`는 서버가 오류 응답을 준 경우(`RestClientResponseException`)만 잡아서, 읽기 타임아웃(`ResourceAccessException`)이 나면 예외가 그대로 올라가 `HoldingTimeExitService.checkAndAlert` 전체를 중단시키는 구조였다. 더 중요한 점은, 주문 POST가 타임아웃이 나면 요청이 서버에 도달했는지 봇이 알 수 없다는 것이다. 실패로 단정하면 이미 접수된 주문을 놓치고, 성공으로 보면 안 나간 주문을 놓친다
- 해결: 타임아웃은 전역으로 넣되(연결 5초, 읽기 30초, 실측하지 못한 가정값) 주문 경로를 함께 고쳤다. `OrderPlacementResult`에 `UNKNOWN`(접수 여부 불명)을 추가해 거부(`FAILED`)와 구분하고, 시간 청산은 `UNKNOWN`이면 즉시 디스코드로 알려 사용자가 증권사 앱에서 직접 확인하게 한다. 주문이 나갔을 수 있으므로 하루 횟수에는 센다. 종목 하나의 예외가 나머지 종목 판정을 건너뛰게 하지 않도록 종목 단위로 막았다. 처음 계획한 "조회용 클라이언트를 따로 분리"는 서비스 9개의 생성자와 테스트를 고쳐야 해서 변경이 크고 주문 쪽은 여전히 무한 대기로 남아, 사용자와 상의해 전역 적용 쪽을 택했다
- 확인한 것: Boot의 `spring.http.clients.*` 설정이 `RestClient.builder()`를 직접 부르는 코드에도 적용되는지는 공식 문서에 없었고(자동 구성된 클라이언트에만 적용한다고만 나옴) 그래서 요청 팩토리에 직접 지정했다. 런타임 클래스패스에 Apache, Jetty, OkHttp가 없어 기존 기본 클라이언트도 JDK `HttpClient`였음을 의존성 조회로 확인했다
- 검증: 로컬 가짜 서버(127.0.0.1, 토스로는 아무것도 나가지 않음)가 응답을 안 줄 때 읽기 타임아웃에서 끊기고 예외 종류가 `ResourceAccessException`(원인 `HttpTimeoutException`)인 것을 테스트로 고정했다. 이 예외 종류가 `UNKNOWN` 판정의 근거이기 때문이다. `OrderPlacementService`의 `catch`를 일부러 다른 예외로 바꾸면 `UNKNOWN` 테스트가 실제로 실패하는 것도 확인했다
- 남은 한계: 타임아웃 값은 토스의 실제 응답 시간을 모르고 정한 가정이고, 토스가 같은 `clientOrderId`의 중복 주문을 거부하는지는 확인 못 했다. 시간 청산은 `UNKNOWN` 뒤 다음 영업일까지 재시도하지 않는다 (docs/todo.md 확인 필요 참고)
- 배운 점: 여러 기능이 공유하는 클라이언트에 전역 설정을 넣을 때는 그 클라이언트를 쓰는 곳 중에 돈이 움직이는 경로가 있는지 먼저 봐야 한다. 무한 대기를 타임아웃으로 바꾸면 "안 끝나는 호출"이 "결과를 모르는 호출"로 바뀌고, 주문처럼 되돌릴 수 없는 요청에서는 그 상태를 실패와 구분해서 사람에게 알리는 처리까지 함께 만들어야 한다

## 설계 하이라이트

### 실주문 다중 잠금
자동 매도는 한 겹이 아니라 여러 겹을 모두 통과해야 실제로 나간다.
- `damdam.orders.live-mode` 기본값 false (모의 실행). 켜려면 `.env`에 직접 추가해야 한다
- 관리 범위 게이트(`ManagedScopeGate`): 기능을 처음 켠 시각 이후에 산 종목만 대상. 그 전부터 갖고 있던 종목은 알림만
- 1회 주문 금액 한도(국내, 해외 각각), 하루 최대 횟수, 연속 손실 시 자동 정지 (`AutoSellGuard`)
- 개발 도구(Claude Code)는 주문 엔드포인트를 직접 호출하지 않는다는 규칙을 문서로 고정하고, 테스트는 실제 주소가 아닌 도달 불가능한 주소를 써서 호출되면 바로 드러나게 했다

### 포지션 시작 시점을 주문 이력에서 복원 (`PositionEntryResolver`)
- 보유 종목의 "보유 시작일"은 API가 직접 주지 않는다. 최근 30일 체결 주문을 FIFO로 리플레이해서 포지션이 0이었다가 다시 쌓인 시점의 첫 매수를 시작으로 판단한다. 같은 종목을 하루에 여러 번 사고파는 매매 스타일도 처리된다
- 조회 범위 안에서 매수 기록을 못 찾으면 "그보다 오래 보유 중"으로 해석하고 알림만 남긴다. 순수 계산 로직이라 가짜 데이터로 단위 테스트한다

### 웹소켓 연결 관리 (`OrderStreamClient`)
- 지수 백오프(최대 30초) + 지터로 재연결. 서버 부하와 동시 재접속 쏠림을 피한다
- 토큰은 클라이언트당 1개만 유효하므로, 재연결 전에 이전 연결을 먼저 닫아야 새 연결이 밀려나지 않는다
- 끊긴 구간의 이벤트는 재전송되지 않는다는 API 특성 때문에, 구독이 확정된 직후 REST로 재동기화해 놓친 체결 기록, 남은 OCO 정리, 누락된 OCO 등록을 한다 (위 10번)

### 테스트 가능한 구조와 CI 전제
- 외부 API를 부르는 실행기(query, listen, export 계열)는 프로필로 분리해서, 기본 빌드와 테스트는 실제 API를 호출하지 않는다
- `.env`가 없는 깨끗한 복제본에서 `./gradlew test`가 전체 통과하는 것을 확인했다 (CI에서 시크릿 없이 돌리기 위한 전제)

### 백테스트 데이터 수집 (`backtest` 패키지)
- 일봉을 `before`/`nextBefore`로 과거까지 페이지네이션. 타임존 오프셋의 `+`가 쿼리스트링에서 공백으로 오인되므로 반드시 인코딩한다
- 429는 `Retry-After`만큼 대기 후 재시도. 종목군은 거래대금 상위에서 ETF/ETN을 걸러 일반 보통주만 남긴다 (안 거르면 대형주 취지와 안 맞는 상품이 섞임)
- 봇과 분석(Python + pandas)은 CSV로만 연결해서 서로의 코드에 의존하지 않는다

### 문서로 남긴 판단의 이유
- 전략 문서에 청산 규칙의 근거, 한계(생존 편향 포함), 실전 전환 기준을 백테스트 결과를 보기 전에 확정한다는 원칙을 적었다. 결과를 본 뒤 기준을 바꾸면 사후 합리화가 되기 때문이다

### 알림과 수동 정지 (`notification`, `control` 패키지)
- 알림 채널은 `Notifier` 인터페이스 뒤에 두고 디스코드 구현체를 꽂았다. 호출하는 쪽(안전장치, OCO 관리, 웹소켓)은 디스코드를 모르고, 테스트에서는 람다 한 줄로 가짜 알림기를 넣는다
- 같은 사건은 10분(600초, `damdam.notification.throttle-seconds`)에 한 번만 나가게 스로틀하고(같은 장애가 반복돼도 알림이 폭주하지 않음), 전송은 별도 스레드로 해서 알림 지연이 매매 경로를 막지 않는다
- 403은 모든 토스 API 호출이 지나가는 공용 `RestClient`의 인터셉터 한 곳에서 감지한다. 호출 지점마다 예외 처리를 넣는 것보다 누락이 없다
- 정지 파일은 재시작 없이 파일 하나로 자동 매도와 OCO 등록을 멈추는 스위치다. 결정 시점마다 파일을 확인하고 상태가 바뀔 때만 알린다. 보호 장치를 걷어내는 OCO 취소는 막지 않고, 존재 여부를 판단할 수 없으면 멈추는 쪽으로 넘어지게 했다. 이미 서버에 등록된 OCO는 계속 동작한다는 한계를 운영 문서에 명시했다

### 백테스트 데이터 범위와 조정 이벤트 (2026-09-21)
- 수집기에 시작일 제한 없이 상한(1만 봉)만 둬서 30종목 중 다수가 1988년부터 받아졌다. 3분할이 종목별 비율(50/30/20%)이라 그대로 쓰면 탐색 구간의 절반 이상이 2000년대 이전 시장이 되는 문제였다. 시장 구조가 바뀐 날(2015-06-15 가격제한폭 확대)을 기준으로 분석 쪽에서 읽을 때 잘랐다. 원본은 그대로 두고 기준만 상수 하나로 바꿀 수 있게 했다
- 액면분할 감지는 "원본 종가 / 수정 종가" 비율의 하루 변화로 한다. 삼성전자 액면분할 경계일이 정확히 나오고 거래량도 같이 조정된다는 것을 실측으로 확인한 뒤 30종목으로 넓혔다. 임계값은 감으로 정하지 않고 변화 크기 분포에서 빈 구간(0.5%~1%에 1건)과 반올림 노이즈 크기를 보고 정했다
- 이 방식의 한계도 같이 기록했다. 토스가 조정하지 않은 사건은 비율이 변하지 않아 감지할 수 없다. 가격만으로는 진짜 급락과 구분되지 않으므로 결과 해석 시 감안한다는 식으로 문서에 남겼다

### 백테스트 엔진과 탐색을 결과 전에 고정하는 설계 (2026-09-21)
- 봉인을 관례가 아니라 코드 구조로 강제했다. 로더는 최종 구간 행을 호출자에게 돌려주지 않고, 탐색 코드는 엔진에 구간을 넘겨 확인 구간 거래는 시뮬레이션조차 하지 않는다. 최종 구간 봉이 섞이면 실행이 멈추는 assert도 둔다
- 탐색 규칙(격자, 건수 하한, 슬리피지, 종료 조건, 동률 규칙, 차선책 정의)을 성과 수치를 보기 전에 문서에 적고 커밋한 뒤 실행했다. 사후에 고를 수 있는 자유도를 줄이고 "언제 무엇이 정해졌는지"를 커밋 이력으로 남기기 위해서다
- 독립 검토 에이전트가 설계 단계에서 잡은 것들: 동시 보유 상한 때문에 하루 진입이 5건을 넘을 수 없어 "상위 5일 비중"이 정보가 없는 지표라는 점, 슬리피지 0에서 탐색하면 익절 체결이 가장 유리하게 계산돼 작은 익절폭이 뽑히기 쉽다는 점, 좌표 하강의 종료 조건과 동률 처리가 사후에 바뀔 수 있다는 점
- 결과 단계에서 얻은 것: 겉보기 양수(+0.234%)가 동시 보유 상한이 급락일 신호를 버리는 효과에 기대고 있음을 상한을 풀어 비교해서 확인했다 (무제한 -0.059%, 상한이 걸러낸 거래 -1.06%). 최댓값 하나를 "찾은 수익"으로 읽지 않고 이웃 조합 평균(+0.074%)과 표준오차를 함께 봤다
- 확인 구간을 여는 스크립트도 한 번만 돌게 코드로 막았다 (결과 파일이 있으면 종료, 차선책은 주 후보가 실패로 기록됐을 때만). 판정 규칙은 결과를 보기 전에 문서에 고정하고 커밋한 뒤 실행했다. 통과 판정이 나왔지만 "결과가 좋을수록 먼저 의심한다"는 절차대로 원인을 쪼개 봤다: 세율 차이는 영향이 작았고, 상위 5종목이 순수익의 84.8%였으며, 오늘 기준 승자 12종목이 +1.505%, 나머지 18종목이 -0.033%였다. 통과라는 사실과 통과의 의미를 분리해서 기록했다
- 결과를 보고 세운 가설을 스스로 반박당한 사례도 남긴다. 동시 보유 상한의 효과를 "급락일 신호를 버리는 시장 필터"로 해석해 명시적 필터를 만들어 봤지만 재현되지 않았다. 해석을 문서에서 정정했다
- 기록 결함도 스스로 잡았다. 시작점을 스윕 전에 미리 평가하는 바람에 시도 로그의 새 평가 수(22)와 실제(23)가 어긋났다. 로그 기준으로 세도록 고치고 재실행해 결과가 같음을 확인했다. 시도 횟수가 결과 해석의 핵심 입력이라 로그가 어긋나면 안 된다는 것을 배웠다

### 청산 사유 추정 (`ExitReasonClassifier`, 2026-09-28)
- 매매 기록 CSV에 여러 전략을 구분할 전략 이름과 청산 사유(익절/손절/시간청산/수동) 컬럼을 추가하면서, 체결 이벤트 자체에는 이 정보가 없다는 문제를 풀어야 했다. 웹소켓/REST 체결 이벤트(`OrderEventSnapshot`, `Order`)에는 orderId, orderType, price는 있어도 조건주문(OCO) ID나 어느 leg가 트리거됐는지 알려주는 필드가 없다
- 시간 청산은 `HoldingTimeExitService`가 자신이 낸 매도 주문의 orderId를 이미 기억해두고 있어서(`pendingAutoSellAvgPrice`), 값을 소비하지 않고 조회만 하는 `isPendingAutoSell()`을 새로 추가해 그대로 재사용했다
- 익절/손절은 직접 알려주는 값이 없어 추정한다. `AtrOcoManagementService`가 OCO를 등록/수정할 때마다 계산하는 익절가/손절가를 심볼별로 기억해뒀다가(`lastKnownPrices`), 매도 체결가가 그 값에 닿거나 넘었으면 익절/손절로, 둘 사이면 수동으로 판정한다. OCO가 트리거되면 조건주문 조회로는 더 이상 그 가격을 못 얻으므로, 반드시 등록/수정 "시점"에 미리 남겨둬야 한다
- 판정은 `syncAfterSellFill()`이 OCO를 정리/갱신해 그 기억을 지우거나 바꾸기 전에 먼저 이뤄지도록 호출 순서를 맞췄다. 순서를 반대로 하면 방금 트리거된 OCO의 가격이 정리 과정에서 사라져 스스로 판정 근거를 지우는 셈이 된다
- 한계를 그대로 남겼다: 서버가 확정해주는 값이 아니라 추정이라 실제와 다를 수 있고, 봇이 시간 청산 매도 접수와 체결 사이에 재시작되면 재동기화로 뒤늦게 찾은 그 매도는 시간청산이 아니라 수동/OCO 비교로 잘못 분류될 수 있다(기존에 감수하기로 한 연속 손실 판정의 한계와 같은 종류, docs/todo.md 참고)
- 배운 점: 서버 API가 안 주는 정보라도, 그 정보를 만들어내는 다른 서비스가 이미 내부에 상태로 들고 있다면(체결 전에 등록한 주문ID, 계산해둔 가격) 새 API 호출 없이 기존 상태를 다른 용도로 다시 읽는 것만으로 풀리는 경우가 있다. 다만 그 상태는 "언제 사라지는지"를 정확히 알아야 하고, 판정 시점을 그보다 반드시 앞에 둬야 한다

### 가상매매 신호 함수와 주문 경로 가드 (`papertrading` 패키지, 2026-09-29)
- 신호 계산(`IchimokuCloudBreakout`, `InstitutionNetBuySignal`)을 API도 시계도 모르는 순수 함수로 두고, 결과에 판정 근거(신호일, 구름 상단, 종가, 평균 거래량, 순매수 합계 등)를 함께 담았다. 나중에 기록 파일에서 "이 신호가 왜 났는가"를 다시 계산해 검증할 수 있고, 손계산과 경계값 테스트가 쉽다
- 입력 검증으로 조용한 오판정을 막았다. 0번 봉의 날짜가 기대한 신호일과 다르면 예외를 던져 낡은 목록이나 신호일 봉이 빠진 목록으로 며칠 전 신호를 판정하는 일을 막고, 매매동향 기록이 하루라도 없으면 0으로 채우지 않고 예외를 던진다. 봉이 모자란 정상 상황(신규 상장)은 전용 예외(`InsufficientCandlesException`)로 분리해서, 호출하는 쪽이 그것만 건너뛰고 데이터 오류는 삼키지 않게 했다
- 거래량 2배와 순매수 3% 비교를 나눗셈 없이 곱셈으로 해서 반올림 오차 없이 경계값(정확히 2배, 정확히 3%)을 판정한다
- 주문 경로 가드(`PaperTradingIsolationTest`)는 소스 텍스트 검사 3종이다: import 허용 목록(새 의존이 필요하면 목록을 일부러 고치게 만듦), 패키지 전이 의존 검사, HTTP 클라이언트와 쓰기 메서드와 리플렉션 금지. 임시로 위반 파일을 넣어 실제로 실패하는지 확인했고, 텍스트 검사라 의도적 우회는 못 막는다는 한계를 문서에 그대로 적었다

### 가상매매 대상 종목군, 데이터 조회 연결, 실측 러너 (2026-09-29)
- 조회 코드를 `papertrading`이 아니라 `stocks`에 두었다. 주문 경로 가드가 `papertrading` 소스의 `RestClient` 계열 이름을 막아서 HTTP 호출, 429 재시도, 예외 변환이 그쪽에 있으면 안 되기 때문이다. `RateLimitRetry`가 429 처리와 예외 변환을 한 곳에서 하고, 호출하는 쪽은 `StockLookupException`만 안다. 가드가 설계를 강제해서 오히려 조회와 판정의 경계가 또렷해졌다
- 집계 단위의 fail-closed: 종목 하나가 실패하면 그 종목만 빼는 것은 당연한데, 전부 실패했을 때 "대상 0개"나 "신호 0건"이라는 정상 결과처럼 돌려주면 조회 장애를 놓친다. 종목군은 통과 종목이 0개면, 신호 판정은 **전략마다** 판정을 끝낸 종목이 50% 미만이면 예외를 던진다. 처음에는 두 전략을 합쳐 세서 전략 A 조회만 죽어도 전략 B가 멀쩡해 보이는 구멍이 있었고, 독립 검토가 지적해서 전략별로 바꿨다
- 검토 지적을 추측으로 받지 않고 실험으로 확인했다: "필드가 빠지면 `false`(정리매매 아님)로 조용히 읽힌다"는 우려는 실제 역직렬화가 예외를 던지는 것을 테스트로 확인해 사실이 아님을 밝혔고, 반대로 "본문이 `{}`이면 NPE"는 코드를 읽어 사실임을 확인하고 고쳤다
- 프로필로만 만들어지는 빈의 조립 오류는 일반 테스트에 안 잡힌다: 조회 러너에 생성자가 둘인데 공개 생성자에 `@Autowired`를 빠뜨렸고, 기본 프로필로는 빈이 만들어지지 않아 모든 테스트가 통과했다. 프로필을 켠 컨텍스트로 빈을 만들어 보는 테스트를 추가하고, `@Autowired`를 일부러 빼서 그 테스트가 실패하는 것을 확인했다
- 확인 못 하는 것은 코드 대신 도구로 푼다: 순위 옵션이 빼는 종목, 일봉과 기관 매매동향의 확정 시각은 명세에 없어서 추측으로 스케줄을 설계하지 않고, 시각별로 돌려 결과를 이어 붙이는 조회 러너를 먼저 만들었다

### 외부 검토 지적을 명세와 코드로 검증한 과정 (저녁 일괄 설계, 2026-09-30)
- 독립 검토(`damdam-reviewer`)의 지적 20여 개를 그대로 따르지 않고 항목마다 근거를 붙여 채택, 변형 채택, 기각으로 나눴다. 대용량 명세는 WebFetch가 잘라내서 `curl`로 `openapi.json` 전체(421KB)를 받아 스키마와 설명 문구를 파이썬으로 직접 검색했다
- 첫 대상은 "트리거 후 지정가가 다음 날까지 유지되는가"였다. 명세에 직접 문장이 없어서 단정하지 않고 "확인 못 함"으로 남겼고, 정황 세 가지(조건주문 요청에 `timeInForce` 없음, 일반 주문 `DAY`는 정규장 종료까지 미체결분 자동 취소, 트리거 주문은 일반 주문 API로 다루는 주문)로 당일 유효 쪽이라고 추정하되 추정임을 문서에 적었다. 이 하나로 리뷰어의 "이월 후 고가 기준 재판정"은 근거가 없어 기각하고 "당일 고가 기준 체결"만 채택했다
- 리뷰어 주장을 다시 계산으로 확인했다: "50건이면 참 평균이 0인 전략도 0.46% 이상이 나올 확률 약 24%"는 2단계 표준오차에서 표준편차를 역산(4.54%)해 정규근사하니 23.7%로 크기가 맞았다. 다만 다른 전략의 표준편차를 빌린 값이라 "20~26%"로만 문서에 썼다
- 리뷰어가 못 본 문제도 검증 중에 나왔다: 실전 주문가는 `TickSizeCorrection`이 호가 단위 아래쪽으로 보정하므로 가상과 최대 1호가 차이가 나고, 낙폭 기준의 근거("보유가 최대 5일이라 미실현 영향이 작다")가 같은 문서의 매도 실패 이월 규칙과 모순이었다
- 내 쪽 오류도 스스로 바로잡았다: 수정주가가 배당 조정을 포함하는지 "확인 못 함"이라고 문서에 적었는데, 커밋 전 2단계 문서를 다시 대조하다 토스 FAQ에 배당락까지 조정 대상으로 적혀 있음을 찾아 정정했다. 확인 못 함이라고 쓰기 전에 이미 문서에 있는 조사 결과를 먼저 찾아봤어야 했다
- 리뷰어 안을 그대로 쓰지 않은 사례: 진입가가 고가보다 높으면 "진입 실패"로 하자는 안은 시가 뒤 하락만 한 손실 거래만 빠져 낙관 편향이 생기므로 "고가로 제한"으로 바꿨다. 슬리피지 재현은 Python 별도 구현이 규칙을 갈라놓으므로 같은 Java 순수 함수를 파라미터만 바꿔 재실행하는 방식으로 바꿨다

### 저녁 일괄 가상매매 순수 로직과 독립 검토 반영 (`papertrading`, 2026-09-30)
- 체결, 청산, 총 노출, 주간 손실 한도, 하루 정산을 모두 슬리피지를 인자로 받는 순수 함수와 불변 record로 만들었다. 진입가가 바뀌면 익절과 손절 경로, 총 노출 한도 판정이 연쇄로 바뀌어 기록만으로는 재현할 수 없으므로, 같은 Java 코드를 슬리피지만 바꿔 다시 돌리는 방식을 택했다 (Python으로 따로 구현하면 규칙이 갈라진다)
- 문서의 규칙 문장마다 손계산 테스트를 하나씩 대응시켰다. 일봉만으로는 장중 순서를 모르므로 같은 날 익절가와 손절가를 둘 다 지나면 손절 우선(비관적), 손절 지정가는 감시가보다 1원 낮은 주문가에 체결이고 갭 하락으로 고가가 주문가에 못 미치면 매도 실패로 남기고 시간 청산에 고정한다
- 테스트가 처음부터 통과해서 오히려 의심했다. 익절 판정의 `>`를 `>=`로 바꾸는 변형을 넣어 해당 테스트가 실패하는 것을 확인했고, 독립 검토가 "살아남을 것"이라고 짚은 경계값(고가와 주문가가 정확히 같을 때, 시가가 주문가나 익절가와 같을 때, 반올림이 정확히 x.5일 때)은 테스트를 추가한 뒤 변형 9개를 하나씩 넣어 전부 잡히는지 직접 돌려 확인했다 (원복 뒤 전체 통과)
- 독립 검토(`damdam-reviewer`)가 짚은 조용한 오류 하나: 하루 정산 결과를 저장한 뒤 같은 날을 다시 넣으면 `barsProcessed`가 두 번 늘어 시간 청산이 하루 일찍 나고 익절과 손절도 이중 판정된다. 포지션에 마지막 처리 봉 날짜(`lastBarDate`)를 두고 이미 처리한 봉이거나 처리일과 다른 날짜의 봉이면 예외로 막았다. 하루를 건너뛴 것은 순수 로직이 거래일 캘린더를 몰라 못 잡으므로 상태 저장 단계의 거래일 단위 확정에 요구사항으로 넘겼다
- 검토 지적을 그대로 따르지 않고 검증한 사례: `Set.copyOf`의 반복 순서가 실행마다 달라질 수 있다는 지적은 직접 확인하지 못했지만(검토도 기억에 근거한 주장), 정렬된 리스트로 돌려주는 편이 어느 쪽이든 안전해서 바꿨다. 주간 손실 한도를 순손익으로 세면 정지가 걸릴 만큼 잃었을 때 이미 낙폭 기준(10%)을 넘은 상태라 통과 여부를 바꾸지 못한다는 지적은 계산으로 맞았고, 어느 쪽으로 정의할지는 결과를 보기 전에 사용자가 정하도록 물어 순손익으로 확정한 뒤 문서에 남겼다
- 규칙에 없던 경우를 조용히 넘기지 않았다: 진입가가 고가보다 높으면 진입 실패가 아니라 고가로 제한(실패로 두면 시가 뒤 하락만 한 손실 거래가 빠져 낙관 편향), ATR이 너무 작아 익절가나 손절가가 진입가와 같아지면 사유(`INVALID_EXIT_PRICES`)와 함께 건너뛰고, 총 노출 한도나 주간 정지로 못 산 신호는 이월하지 않고 사유별로 기록한다

### 가상매매 상태 저장과 CSV 기록: 재실행해도 기록이 틀어지지 않게 (`PaperLedger`, 2026-09-30)
- 목표: 하루 한 번 돌리는 가상매매가 중간에 죽거나, 같은 날 두 번 돌거나, 조회가 실패해도 통과 판정에 쓰일 기록(거래 50건, 평균 순수익)이 조용히 중복되거나 빠지거나 편향되지 않게 한다. 순수 로직은 이미 있었고 이번 조각은 그것을 상태 파일과 CSV로 감싸는 부분이다
- 확정 순서: CSV를 먼저 쓰고 상태 JSON을 임시 파일에서 원자적으로 교체하는 것이 마지막(커밋 지점)이다. 그 사이에 죽으면 그 거래일을 처음부터 다시 계산하고, CSV는 결정적 키(전략, 종목, 신호일)의 같은 행을 무시하므로 두 번 쌓이지 않는다. 미완료 정산(봉이 없는 종목이 있는 날)은 결과를 저장하지 않는다. 저장하고 같은 날을 다시 넣으면 순수 로직의 이중 처리 가드가 예외를 내기 때문이다
- 독립 검토(`damdam-reviewer`)가 내 첫 구현에서 높음 3건을 찾았고 코드를 읽어 모두 사실임을 확인한 뒤 고쳤다
  - **포기 횟수가 "날짜"가 아니라 "실행 호출 횟수"였다.** 클래스 주석은 "하루 한 번 실행이라 3거래일치"라고 적었지만 코드는 그것을 보장하지 않았다. 작업 스케줄러가 재시도하거나 수동으로 세 번 돌리면 몇 분 만에 보유 포지션이 영구 포기로 넘어간다. 마지막으로 센 달력 날짜를 상태에 저장해 같은 날 재시도는 세지 않게 했다
  - **조회 전체가 죽어도 종목이 일괄 포기됐다.** 집 IP가 바뀌어 403이 나거나 휴장일을 거래일로 넘기면 모든 종목이 "봉 없음"인데, 종목별로만 세니 3번째 실행에서 표본이 통째로 사라진다. 봉 맵이 통째로 비면 종목이 아니라 조회 전체의 결측으로 보고 세지도 포기하지도 않고 멈추게 했다. 대신 호출자가 기준 종목의 봉을 함께 넘겨야 한다는 규약이 생겼다
  - **포기한 포지션이 CSV 어디에도 없어 통과 판정이 위로 치우칠 수 있었다.** 포기는 대개 상장폐지나 장기 정지라 큰 손실인데, 청산된 것만 거래로 세므로 평균에서 빠지고 총 노출에서도 빠져 새 진입이 늘어난다. `abandoned` CSV로 남기고, 결과를 보기 전에 사용자와 두 규칙(총 노출에 계속 포함, 통계에는 마지막 종가로 청산한 것으로 포함)을 문서로 확정했다
- 조용한 넘김을 막았다: 같은 키에 다른 내용의 행이 오면(잠정 일봉이 확정치로 바뀐 뒤 재실행 등) 무시하지 않고 예외를 던진다. 어느 쪽이 맞는지 이 계층은 알 수 없고, 무시하면 CSV에는 옛 거래가 남고 상태에는 새 거래가 들어가 둘이 갈라지기 때문이다. 같은 이유로 슬리피지와 전략 버전을 바꿔 같은 폴더를 열면 거부한다 (진입은 옛 슬리피지, 청산은 새 슬리피지인 혼합 방지)
- 시간대 검증에서 함정 하나: 같은 날 재시도 판정에 `Clock`의 달력 날짜를 쓰는데, UTC 시계는 서울 자정부터 아침 9시 사이에 전날 날짜를 준다(실제로 서울 10/1 01:00에 UTC 시계는 9/30이 나옴). 처음 생각한 `ZoneId` 동등 비교는 `+09:00` 오프셋 시계를 "다른 시간대"로 거부한다는 것을 직접 실행해 확인하고, 그 시각의 UTC 오프셋이 +09:00인지 보는 방식으로 바꿨다. 서버 이전 뒤 기본 시간대가 UTC인 서버에서 `Clock.systemDefaultZone()`을 쓰는 실수도 시작할 때 막힌다
- 테스트가 한 번에 통과해서 의심했다. 포기 횟수를 2와 4로 바꾸기, 같은 날 재시도도 세기, 조회 전체 결측 판정 제거, 같은 키 다른 내용 무시, 잠금 확인 제거, 버전 혼합 허용, 시간대 검사 제거를 하나씩 코드에 넣고 각각 테스트가 실패하는 것을 확인한 뒤 원복했다 (전체 388건 통과)
- 검토 지적을 그대로 따르지 않은 사례: "done.md와 troubleshooting.md의 배당락 서술이 서로 다르다"는 지적은 사실과 달랐다. 실제로 어긋나는 것은 토스 FAQ 문구(배당락 조정 대상)와 done.md의 삼성전자 실측(배당 미반영으로 보임)이었다. 그래서 보정 규칙에 "확인 못 함"을 명시하고 실제 배당락 종목의 `adjusted` 캔들 비교를 할 일로 남겼다. 반대로 "거래정지일에 봉이 오는지 확인 못 함"이라는 지적은 2단계 데이터(427일, 거래량 0 봉)로 이미 확인된 사실이라 근거를 문서에서 찾아 답했다
- 남긴 한계: 수정주가 보정이 아직 없어 보유 중 액면분할이나 배당락이 나면 가짜 손절이 기록될 수 있고(러너 조각에서 구현), 신호 생성 게이트와 러너, 봉이 안 와 막힌 날의 신호 소실(순위 API는 소급이 안 됨)은 다음 조각의 몫이다. 모두 docs/todo.md에 규약으로 적어 두었다
- 배운 점: "하루 한 번 실행된다"는 가정을 주석에만 적으면 코드는 그것을 지키지 않는다. 재시도, 수동 실행, 시간대 같은 운영 현실이 가정을 깨므로 가정을 상태와 검사로 만들어야 한다. 그리고 실패했을 때 "조용히 정리"하는 동작(일괄 포기, 같은 키 무시, 빠지는 통계)은 표본을 조용히 바꾸므로, 파괴적 결정일수록 그 근거가 되는 신호(조회 전체가 죽지 않았는가)를 먼저 확인하고 멈추는 쪽을 기본으로 둬야 한다

### 서버 배포 방식: 사용자 제안(Actions 자동 배포)을 검증해 범위를 줄인 과정 (2026-10-02)
- 상황: AMD 무료 서버는 메모리 1GB라 서버에서 gradle 빌드를 하면 부족할 수 있다는 지적이 나왔고, 사용자가 "GitHub Actions로 빌드해서 올리면 되지 않냐"고 제안했다
- 검증한 것: 오라클 공식 문서로 메모리 1GB와 ARM 무료 한도(합계 2 OCPU, 12GB)를 확인했다. 로컬에서 Gradle 힙을 384MB, 256MB, 64MB로 줄여 빌드해 보니 256MB까지는 성공하고 64MB에서 실패해서 인자가 실제로 적용되는 것도 확인했다. 단 이것은 힙만 잰 것이라 서버에서 실제로 부족한지는 확인 못 함으로 남겼다
- 제안을 둘로 나눠 판단했다. "Actions가 jar를 빌드한다"는 채택했다(공개 저장소라 무료이고 jar에는 환경변수 자리표시자뿐이라 비밀값이 없다). "Actions가 SSH로 서버에 자동 배포한다"는 채택하지 않았다. 이유는 세 가지다. GitHub 공식 문서가 러너 IP는 수시로 바뀌어 IP 허용을 권하지 않는다고 해서 22번을 사실상 전 세계에 열게 되고, GitHub에 서버 SSH 개인키를 둬야 하며, push마다 실주문 봇이 장중에도 교체될 수 있다
- 구현: `release-jar.yml`은 수동 실행에서만 돌고 테스트가 통과해야 jar와 sha256을 릴리스에 올린다. 입력한 태그는 스크립트에 직접 끼우지 않고 환경변수로 받아 `v숫자.숫자.숫자` 형식만 허용한다 (스크립트 주입 방지, 이 정규식은 `v0.1.0;rm` 같은 값을 거르는 것까지 확인). 서버는 `curl`로 받고 사용자가 장 마감 후 직접 재시작한다
- 남긴 한계: 워크플로는 아직 한 번도 실행하지 않았다 (YAML 구문만 검사). sha256은 전송 중 손상만 막고 GitHub 자체가 뚫린 경우는 막지 못한다. 서버 쪽 JVM 상한 `-Xmx256m`이 충분한지는 실측 전이다
- 배운 점: 편해 보이는 자동화는 "어디까지 자동으로 맡길 것인가"를 나눠서 봐야 한다. 빌드 자동화는 위험이 거의 없지만 배포 자동화는 접근 권한(키, 열린 포트)과 실주문 시점 통제를 함께 바꾼다. 돈이 움직이는 시스템에서는 사람이 재시작 시점을 정하는 한 단계를 남기는 쪽을 기본으로 둔다
