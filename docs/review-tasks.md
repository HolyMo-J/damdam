# 리뷰 작업 목록

완료 표시 방법: 항목 번호 뒤에 `[완료 YYYY-MM-DD]` 태그를 붙인다. 예: `1. [완료 2026-09-30] 서버 시간대...`
새 세션에서는 이 파일을 읽고 아래 "진행 순서"에서 완료 표시가 없는 첫 항목부터 이어간다.

---

아래 E묶음은 다른 Claude 대화에서 이 저장소를 리뷰하고 사용자와 논의해서 정한 내용이다. 그 Claude는 저장소를 읽기만 했고 빌드, 테스트, 실제 API 호출, 서버 확인은 하지 못했다. 그래서 틀린 내용이 섞여 있을 수 있다. 이전 D묶음은 2026-09-28에 모두 처리되어 파일이 삭제됐고, 이번에 E묶음만 새로 담아 다시 만들었다.

시키는 대로 그대로 고치지 말고 항목마다 이렇게 진행한다.
- 먼저 실제 문서와 코드, 공식 문서로 내용이 맞는지 직접 확인하고 근거를 보여준다.
- 틀렸거나 과하다고 판단되면 고치지 말고 이유를 말한다.
- 파일을 만들거나 수정하기 전에 방향을 사용자에게 먼저 확인하고, 선택지를 낼 때는 권장하는 쪽을 같이 적는다.
- 실제 돈이 움직이는 코드는 보수적으로 판단하고, 확신이 없으면 고치지 말고 물어본다.
- 커밋 메시지는 한글로 쓴다. 추측으로 채우지 말고 모르는 건 공식 문서를 확인하거나 사용자에게 물어본다.

진행 방식
- 항목 하나가 끝나면 멈추고 요약한다. 문서만 바꾸는 항목은 한 세션에서 이어서 해도 된다.
- 5번, 10번은 설계안만 먼저 보여주고 구현 전에 사용자에게 묻는다.
- 진행 중 새로 발견한 문제는 docs/todo.md의 나중에 항목에 한 줄로만 기록한다. 돈이 잘못 움직이거나 손절 보호가 사라질 수 있는 문제는 바로 알린다.
- 항목 하나가 끝나면 `finish-task` 스킬로 마무리한다 (테스트, 커밋 승인, 이 파일의 완료 표시, todo/done 갱신).

진행 순서 (2026-09-30 사용자가 Claude 권장안으로 승인): 7, 8, 9, 11, 10, 그다음 1, 2, 3, 4, 5, 6
- 7번은 가상매매 결과를 보기 전에 정해야 해서 가장 먼저 한다. 8, 9번은 7번과 같은 docs/strategy.md 문서 작업이라 이어서 한다.
- 11번, 10번은 서버 없이 가상매매를 빨리 시작하는 것과 이어진다.
- 1~6번은 서버 배포 관련이라 서버 이전이 진행될 때 함께 처리한다.

E묶음

서버 배포 관련

1. [완료 2026-10-02, (가)+(나) 둘 다 적용] 서버 시간대. 오라클 우분투 이미지 기본 시간대가 UTC일 가능성이 있다는 지적이다 (미검증, 공식 문서로 확인). 코드에 시스템 기본 시간대로 오늘 날짜를 구하는 곳이 있다: AutoSellGuard의 Clock.systemDefaultZone, HoldingTimeExitService, OrderService, AtrOcoManagementService의 LocalDate.now. 서버가 UTC면 하루 자동 매도 횟수가 한국 시간 오전 9시에 초기화되는 식으로 어긋난다.
- 두 방법을 비교해 권장안을 제안한다: (가) docs/deploy.md에 서버 시간대를 Asia/Seoul로 설정하는 단계 추가, (나) 코드에서 한국 시간대를 명시. 둘 다 할 수도 있다.

2. [완료 2026-10-02, 사용자 제안으로 Actions 빌드 + 릴리스 다운로드 방식 채택, 자동 SSH 배포는 채택 안 함] 1GB 메모리. AMD 무료 인스턴스는 메모리가 1GB라서 서버에서 gradlew bootJar 빌드 중 메모리가 부족할 수 있다는 지적이다 (미검증).
- 집 PC에서 jar를 빌드해 서버로 올리는 방법과 스왑을 추가하는 방법을 비교해 docs/deploy.md에 반영하는 안을 제안한다.
- 서비스 파일의 JVM 최대 메모리 설정도 제안한다.
- ARM 인스턴스를 만들면 해당 없다는 점도 적는다.

3. [완료 2026-10-03, docs/deploy.md 6절 초안, 서버에서 시험은 못 함] 서버 보안 기본값. 서버에 토스 API 키가 올라가는데 docs/deploy.md에 아래 단계가 없다. 추가하는 안을 제안한다.
- .env 파일을 본인만 읽을 수 있게 권한 설정
- SSH는 키로만 접속하고 비밀번호 로그인 끄기
- 22번 외 인바운드 포트는 열지 않기. 오라클 보안 목록 기본값이 어떤지 공식 문서로 확인한다.

4. [완료 2026-10-03, docs/deploy.md 7절 초안, 방법은 집 PC가 당겨 오는 방식을 권장, 서버에서 시험은 못 함] 거래 기록 백업. 서버로 옮기면 records 폴더의 거래 기록 CSV와 bot/data의 안전장치 상태가 서버에만 남고, 저장소가 공개라 git에도 안 올라간다. 오라클이 유휴 인스턴스를 회수하거나 서버를 다시 만들면 v1 판단과 가상매매 판단에 쓸 기록이 사라질 수 있다.
- 하루 한 번 집 PC나 비공개 저장공간으로 복사하는 방법을 비교해 권장안을 제안한다.
- 토큰 파일은 백업 대상에서 뺀다. 백업 위치가 공개되면 안 된다. 가상매매 기록도 같은 방식으로 백업한다.

5. 외부 하트비트를 서버 배포와 같이 진행하는 것으로 우선순위를 올린다. docs/todo.md 나중에 항목에 이미 설계 메모가 있다. 서버는 아무도 보지 않아서 회수나 크래시로 조용히 죽으면 시간 청산과 가상매매가 며칠씩 멈춰도 모를 수 있다.
- 설계안만 먼저 보여주고 구현 전에 묻는다. 서비스 선택과 무료 조건은 공식 문서로 확인한다.

6. [완료 2026-10-03, 사용자 결정: 기한은 오라클 티켓 답변이 올 때까지, 날짜는 정하지 않음] 서버 결정 기한을 docs/todo.md 서버 이전 항목에 적는다. 오라클 가입이 계정 확인 문제로 티켓 답변을 기다리는 중이다.
- 날짜는 사용자에게 물어본다. 그 날짜까지 답이 없으면 유료 VPS인 Vultr로 간다고 적는다.
- Vultr는 월 5에서 6달러이고 서울 리전이 있다는 것이 다른 Claude의 설명이다. 요금과 서울 리전은 공식 문서로 다시 확인한다 (미검증).

전략과 통과 기준 관련

7. [완료 2026-09-30] 3단계에서 4단계로 넘어가는 기준 정리. 새 가상매매 설계는 50건 이상에서 거래당 평균 순수익 0.46퍼센트 이상만 보는데, 기존 docs/strategy.md 백테스트 통과 기준에는 최대 낙폭 10퍼센트 이하, Calmar 비율, 벤치마크 비교까지 있어서 두 기준이 갈려 있다.
- 가상 계좌의 최대 낙폭 10퍼센트 이하를 추가하는 안을 권장받았다. 평균만 보면 한 번 크게 잃는 전략을 걸러내지 못하기 때문이다.
- 가상매매 결과를 보기 전인 지금 정해야 한다. 기존 기준 중 무엇을 가상매매에 적용하고 무엇을 빼는지 정리해서 사용자에게 묻는다.

8. [완료 2026-09-30] 전략 두 개를 동시에 시험하면 둘 중 하나는 운으로 통과할 확률이 올라간다. 그래서 통과한 전략도 소액 실전 첫 50건을 두 번째 검증 구간으로 본다고 docs/strategy.md에 적는다. 이미 정한 증액 조건(거래 50건 이상, 비용 반영 거래당 평균 손익 플러스)이 이 재검증 역할을 한다는 점을 연결해서 적는다.

9. [완료 2026-09-30, 적용 안 함: 전제가 기존 문서와 충돌] 실전 신호 선택 규칙. 가상매매는 전략별 50만원에 동시 보유 5종목이지만, 실전 자금은 10만원이라 한 번에 한 종목만 살 수 있다. 신호가 여러 개인 날 가상매매와 같게 거래대금이 큰 순서로 고르는 안을 docs/strategy.md에 넣는다. 실전 매수는 사용자가 직접 하므로 봇이 알려주는 방식이 된다.

가상매매를 빨리 시작하는 방법

10. [완료 2026-09-30, 설계 채택과 문서 반영까지. 구현은 별도] 가상매매를 서버 없이 저녁 일괄 처리로 먼저 시작하는 방안을 검토한다. 두 전략 모두 신호를 장 마감 후 일봉으로 정하니, 청산 체크도 저녁에 하루 한 번 일봉 고가와 저가로 할 수 있고, 집 PC에서 저녁에 한 번 돌려도 된다.
- 매수가는 아침 매도 1호가 대신 다음 날 시가에 슬리피지를 더한 값으로 근사한다. 슬리피지 값은 근거와 함께 제안한다.
- 같은 날 익절가와 손절 감시가를 둘 다 지났으면 손절을 먼저로 보는 기존 백테스트 규칙을 따른다. 갭 하락 손절은 docs/records.md의 가상 체결 규칙대로 매도 실패 처리한다.
- 기존 설계의 실주문 경로 차단 원칙은 그대로 지킨다.
- 저녁 일괄 방식과 서버 실시간 방식의 차이를 정리하고, 나중에 실시간으로 바꿀 때 기록 비교가 가능하게 방식 이름을 기록에 남기는 안을 제안한다.
- 설계안을 먼저 보여주고 구현 전에 묻는다. 채택하면 docs/strategy.md 3단계 설계도 고친다.

11. [완료 2026-09-30] 전략 B 신호 빈도를 지금 미리 센다. 전략 B는 일봉만 쓰니 기존 분석 코드와 캔들 데이터로 과거 신호가 한 달에 몇 건 나오는지 셀 수 있다.
