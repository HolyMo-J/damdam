# damdam 점검 절차

범용 절차(실행 전 세 문장, 수치 읽고 넘어가기, 놀라운 값 절차, 독립 검토 요령)는 전역 `assumption-review` 스킬을 먼저 불러와 그대로 따른다. 이 문서는 damdam 전용 항목만 더한다. 코드가 돌아가는지가 아니라 **전제가 맞는지**를 점검한다.

## 데이터
- 범위: 시장 구조가 바뀐 시점 이전 데이터가 섞이지 않는가 (예: 2015-06-15 가격제한폭 ±15%에서 ±30%로 확대, 그 전에는 토요일 장도 있음)
- 한도에 걸린 값: 봉 수가 정확히 10000이면 데이터 한계가 아니라 수집기 상한에 잘린 것이다
- 생존 편향: 종목군이 "오늘 기준"으로 뽑혀 과거 상장폐지, 부진 종목이 빠지지 않았는가
- 조정: 액면분할, 증자, 감자가 반영됐는가. 조정되지 않은 사건은 가격만으로 못 걸러낸다는 한계를 아는가
- 결측과 거래정지: 거래량 0인 날, 주말/휴일 봉, 중복 날짜가 있는가
- 단위와 통화: 원, 달러, 주 단위, 퍼센트 대 비율을 섞지 않았는가

## 백테스트
- 룩어헤드: 신호일에 알 수 없는 정보(당일 종가 이후, 미래 평균)를 쓰지 않는가
- 봉인: 최종 검증 구간을 코드가 로드하지 않는가. 결과를 본 뒤 기준을 바꾸지 않았는가
- 시도 횟수: 몇 번 시도했는지 기록하는가 (docs/strategy.md에 남긴다)
- 비용: 수수료와 매도세 0.20%를 반영했는가
- 표본: 건수가 충분한가. 특정 종목이나 시기에 쏠리지 않았는가

## 돈이 움직이는 코드
- CLAUDE.md 보안 규칙을 지키는가 (실제 주문 호출 금지, 기본값은 주문 안 보내는 모드, 금액과 횟수 한도)
- 봇이 재시작되거나 연결이 끊겨도 상태가 안전한가
- 실패했을 때 조용히 지나가지 않고 알리는가

## 독립 검토
데이터 수집/가공 설계, 백테스트 파라미터와 결과 보고, 주문 관련 코드는 `damdam-reviewer` 에이전트에게 검토를 맡긴다. 프롬프트에 담을 것과 지적을 다루는 방법은 `assumption-review`의 "독립 검토가 필요하면"과 같다. 지적은 그대로 따르지 않고 실제 코드와 데이터로 검증한 뒤 판단한다 (CLAUDE.md 작업 규칙).

## 사고 사례: 1988년 데이터 (2026-09-21)
수집기에 시작일 제한 없이 상한(1만 봉)만 두어서 30종목 중 다수가 1988년부터 받아졌다. 이전 세션에서 "1988년부터인 종목이 있다"를 데이터 특성으로 기록했지만, 실제로는 수집기 상한에 잘린 값이었고 시장 구조도 지금과 달랐다. 세 문장의 두 번째("많이 받아두면 좋다")를 적었다면, 그리고 봉 수가 정확히 10000인 것을 이상하게 봤다면 막을 수 있었다.
